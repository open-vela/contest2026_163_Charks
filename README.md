# 小满 —— 板端全自持的儿童实时语音陪伴机器人

> 参赛队：`contest2026_163_Charks`
> 赛道：**AI 硬件产品创新**
> 平台：Rivotek Gemini-S1（全志 R528 双核 A7）+ openvela / NuttX

---

## 一、作品简介

**小满**是一个面向 2~3 岁幼儿的语音陪伴机器人。孩子对着它说话，它听得懂、
会用儿童化的口吻回话、脸上会有表情；它还能感知孩子的情绪（开心、难过、害怕）、
在听到不适合幼儿的话题时**主动把话题引开**。

技术上它最大的特点是：**整条实时语音链路完全跑在板子上，不需要任何服务器中转。**

```
孩子说话 ──▶ 麦克风 16kHz ──▶ 重采样到 24kHz ──▶ WebSocket ──▶ StepFun Realtime
                                                                    （StepAudio 3）
孩子听到 ◀── 喇叭 16kHz  ◀── 重采样到 16kHz ◀── WebSocket ◀── 模型直接生成语音
                                                    ＋ 表情 / 情绪 / 安全改舵
```

板子自己完成 **TLS 握手 → WebSocket → 鉴权 → 会话配置 → 音频上下行 → 重采样**，
中间没有任何一台服务器。这一点是刻意的取舍，理由见第二节。

### 亮点

| 亮点 | 说明 |
|---|---|
| **无网关直连** | 板子直接连 `api.stepfun.com`，少一跳依赖，音频不经过任何第三方服务器 |
| **密钥不进固件** | 固件里没有 API Key，开机从 `/data`（可写分区）读，换 key 只要推一个文件 |
| **抗"网络时间"故障** | 板子没有 RTC，开机是 1970 年；证书校验会以"看起来像证书坏了"的方式失败。做了三层兜底（见下） |
| **儿童安全** | 命中敏感话题时**在模型开口之前**插内部提示改舵（实时语音没法事后过滤文本） |
| **情绪引擎** | 从孩子和模型的用词推算心情三轴，驱动表情与配色 |

## 二、选题方向

**AI 硬件产品创新。**

选这个方向的理由：本项目关注的不是"把模型跑在板子上"，而是
**"一个真实的儿童设备，在真实的家庭网络里，能不能长期稳定地用起来"**。

过程中踩到的坑几乎全部与模型无关 —— 全在时间、网络、驱动、总线这类
"产品化"的地方（见第五节）。这些坑才是从 demo 走到产品的距离，
也是这个作品真正想沉淀的东西。

### 为什么不做网关中转（架构取舍）

最初的设计是「板子 → 云上网关 → StepFun」。后来改成了板子自持，理由：

1. **API Key 的安全边界不因为网关而改变。** 只要 key 在设备上，它就不再是秘密
   （实证：把固件 `strings` 一下就能抓到里面的 WiFi 明文密码）。
   所以 key 干脆不进固件，改从 `/data` 读。
2. **少一跳就少一类故障。** 网关是公网服务，会引入可用性、延迟、计费三重依赖。
3. **代价要说清楚**：板子到 StepFun 这段是**公网直连、明文数据在应用层**，
   由 TLS 保护（TLSv1.2 / ECDHE-RSA-AES128-GCM-SHA256）。

## 三、目录结构

```text
app/superchild/          板端应用（本作品的主体）
├── sc_main.c            入口：UI 主任务 + 采集 / 播放 / 实时会话 / WiFi 守卫 四个任务
├── sc_rt.c              编排：半双工闸门、音频泵、重连、空闲表情、界面投递
├── sc_stepfun.c         StepFun Realtime 会话（session.update / 上下行音频 / 打断）
├── sc_ws.c              自写 WebSocket 客户端（该移植层的 cwebsocket 只有 patch 没源码）
├── sc_tls.c             TLS 封装 + 内嵌 DigiCert Global Root G2 根证书
├── sc_time.c            时间获取：SNTP → HTTP Date → /data 持久化（三层兜底）
├── sc_resamp.c          16k⇄24k 定点重采样（多相 FIR + Blackman 窗，48k 中间域）
├── sc_b64.c / sc_port.c Base64；可移植薄层（宿主与板端共用）
├── sc_audio.c           ALSA 采集 / 播放 + 环形缓冲 + 电平
├── sc_microute.c        麦克风通路使能（R528 必踩的坑）
├── sc_face.c            表情界面（唯一碰 LVGL 的地方）
├── sc_key.c             API Key 从 /data 读
├── sc_emo.c / sc_safety.c  情绪判定 / 儿童安全
├── sc_wifi.c            联网守卫
├── sc_disp.c            显示相关诊断
└── test/                宿主自测（可在 PC 上原生编译运行）

scripts/                 构建与集成脚本
docs/                    开发过程中的全部技术文档（含踩坑复盘）
logs/                    AI Coding 日志（见第六节）
```

**编译映射**：`app/superchild` 由 `contest2026_163_Charks.xml` 软链到
`packages/demos/contest2026_163_superchild`，**公共仓库零改动**。

## 四、运行方式

### 4.1 拉取工程

```bash
repo init -u https://github.com/open-vela/contest2026_163_Charks \
  -b dev-ai-contest-2026 -m contest2026_163_Charks.xml
repo sync -c -j8
```

### 4.2 编译

```bash
cd ..
OPENVELA_SRC=$PWD
# 把应用接进构建树（幂等，可重复执行）
WIFI_SSID='<你的WiFi名>' WIFI_PASS='<你的WiFi密码>' \
  bash contest2026_163_Charks/scripts/integrate_superchild.sh

# 编译（产物：rtos_nuttx_<board>_uart0_*nand.img）
bash scripts/ecs_build.sh
```

> WiFi 凭据**通过环境变量传入，不写进仓库**。集成脚本只在显式给了
> `WIFI_SSID` 时才写入。

### 4.3 烧录与首次配置

烧录会**全盘擦除**，`/data` 分区跟着没了。而按设计 API Key 不在固件里，
所以**每次刷机后要推一次**：

```bash
# 建目录并写入你的 StepFun API Key（单独一行）
adb shell "mkdir -p /data/etc/superchild"
adb shell "echo <你的Key> > /data/etc/superchild/stepfun.key"

adb shell reboot
```

仓库里附了脚本把这一步变成一条命令（含**回读校验**）：

```bat
scripts\restore_device.bat
```

### 4.4 上电后应当看到

```
上电 → 屏幕出现一张脸
     → WiFi 自动连上（守卫会一直重试到成功为止）
     → 自动同步系统时间（SNTP）
     → 自动连接 StepFun，建立会话
     → 开口说「你好呀，我是小满，我们一起玩好不好？」
     → 之后直接说话即可对话（服务端 VAD 自动断句：门限 700、静音 800ms）
```

排查时看串口关键字：`time: / tls: / ws: / rt: / stepfun: / mic:`。

## 五、AI Coding 使用说明

本作品的开发**全程由 AI 结对完成**。完整对话日志见 `logs/` 目录。

### 5.1 各环节怎么协作

| 环节 | 怎么用 AI |
|---|---|
| **需求拆解** | 把"做个儿童陪伴机器人"拆成可验证的小步，每步都定"怎么算做完了" |
| **方案设计** | 用它横向对比架构选项（网关 vs 板子自持），并把取舍写下来 —— 尤其是**代价**那一栏 |
| **编码** | 协议栈（TLS / WebSocket / 重采样 / 时间同步）大部分由 AI 写出，人负责审关键路径 |
| **调试** | **这是收益最大的地方**：AI 负责把"现象"变成"可测量的数"，见 5.2 |
| **文档** | 所有踩坑复盘由 AI 在排查过程中同步记录，避免事后回忆失真 |

### 5.2 这次真正的经验：**不要让 AI 猜，要让它造仪器**

项目里有一个反复出现的模式，值得单独说：

> **同一个现象，往往有好几种原因，而且它们的表象完全一样。**

例如"说了没反应"，可能是：麦克风没采到 / 采到了但太轻 / 上行没送出去 /
服务端没识别。四者的串口输出**一模一样**，全是沉默。

我们在这上面栽过几次，最典型的一次是屏幕卡顿：

| 轮次 | AI 的判断 | 结果 |
|---|---|---|
| 1 | "肯定是背景色每帧触发整屏重绘" | 改完**没解决** |
| 2 | "那是 CPU 竞争，得调任务优先级" | **又错了** |
| 3 | 先加埋点，把一帧拆成「设属性 / 渲染 / 刷屏」分别计时 | 发现：**设属性 0ms、纯渲染 1.4ms、刷屏 418ms** |
| 4 | 按数据修 | 真正的原因（每帧都重设全部控件属性 → 每帧判脏 → 每帧整屏写入）暴露出来 |

前两轮之所以都错，是因为 AI 在**一个混在一起的数字**上做推理。
第三轮把数字拆开之后，推理这一步就被消掉了。

**结论**：AI 很擅长"造一个能分辨 N 种原因的仪器"，不擅长"凭现象猜原因"。
把精力从后者挪到前者，效率完全不同。

### 5.3 AI 带来的实际收益（量化）

| 项 | 说明 |
|---|---|
| 协议栈自研 | TLS / WebSocket / 定点重采样 / 时间同步，一个晚上从零跑通（板端实测） |
| 排障 | 把"凭感觉改"变成"先埋点再改"，少了好几轮无效编译刷机 |
| 文档 | 每个坑的**报错现象 / 真实原因 / 修法**三件套同步入库，可直接给后人看 |
| 反例 | 见 5.2 —— AI 也会一错再错，**必须要求它给证据** |

### 5.4 一个刻意的纪律

**所有结论必须标明是"实测"还是"推断"。** 项目文档里凡是推断的都会写"未验证"，
实测的会附上串口原文。这条纪律来自一次教训：

> 同一个"重采样写错了"和"测试信号超出语音带宽"，在现场是分不清的；
> 而当时 AI 给出的判断很自信，却是错的。**要求在文档里标注证据等级之后，
> 这类"自信的错"少了很多。**

## 附：开发中踩到的坑（全部实测，欢迎直接抄结论）

> 完整复盘在 `docs/` 里。这里只列最"反直觉"的几条 ——
> 它们的**报错都指向错误的方向**，这是最耗时间的一类问题。

| # | 报错现象 | 看起来像 | 实际是 |
|---|---|---|---|
| 1 | 采集报 `capture only support 1~3 channel` | 声道数配错了 | R528 混音器的麦克风通路**默认全 Off 且不持久化**；跟声道数毫无关系，改 `-c 1/2/3` 报同一个错 |
| 2 | `certificate validity starts in the future` | **证书本身有问题** | 板子没有 RTC，开机是 1970 年 |
| 3 | NTP `samples` 永远是 0 | NTP 服务器挂了 | `CONFIG_NETUTILS_NTPCLIENT_SERVERIP` 的 Kconfig 是 `depends on !LIBC_NETDB`，而板子开了 DNS → **这一项根本不存在，写进去被静默丢弃**；实际用的是默认值 `0.pool.ntp.org`（国内连不上） |
| 4 | WiFi 配了却连不上 | 密码或信号问题 | 板子上有一份**在打包素材里、每次刷机都会回来**的 `wapi.conf`，写死了别的 AP 的 BSSID，且**优先于编译期配置** |
| 5 | DHCP 超时拿不到 IP | 路由器问题 | netinit 触发关联后**不等链路建立就去跑 DHCP**，而 Realtek 驱动是异步关联的 |
| 6 | 表情"一卡一卡" | CPU 不够 / 屏不行 | 每帧重设全部控件属性 → 每帧判脏 → 每帧整屏写入 |
| 7 | 改了代码但现象不变 | 代码没生效 | 用 `strings <img> \| grep 中文` 检查中文日志串会得到**假的 0** —— `strings` 默认只输出 ASCII，必须用 `grep -a` 扫原始二进制 |
| 8 | 构建日志里 `error:` 数为 0 但没产物 | 编译成功 | 链接器挂了、没产出 ELF。**判断构建成功要看 ELF 是否存在，不能只看 error 数** |
