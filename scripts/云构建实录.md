# 云构建实录 —— 从零到可烧录镜像踩过的 13 个坑

> 本文记录**实际构建**（不是设想）中遇到的每一个问题：现象、诊断过程、根因、修法。
> 目的是下一次构建时不必重新踩一遍。
>
> 结果：**一次性走通全链路，产出 31.9MB 可烧录镜像**
> `firmware/rtos_nuttx_r528s3-gemini-s1_uart0_128Mnand.img`
>
> 主要脚本：`scripts/build_openvela.sh`（主流程）、`install_pack_deps.sh`（打包依赖）、
> `fetch_lfs_libs.py`（补 LFS 库）、`remote_build_job.sh`（远端任务管理）。

## 总览

| # | 现象（一眼看不透的） | 根因 | 修法 |
|---|---|---|---|

## 零、从零重建的完整步骤（云主机释放后用这份）

> 云主机已释放。**这台机器的所有信息都不依赖它本身** —— 源码可用 `repo sync` 重取，
> 构建脚本、补丁、文档全在本仓库，所以重建是纯流程性的，不需要重新摸索。

**准备一台新实例**（要求见《云主机构建指南.md》）：Ubuntu 22.04 **原生**（WSL/Docker 会被拒）、
x86_64、≥16GB 内存、**系统盘 ≥60GB**。

```bash
# ① 把本仓库的构建套件传上去
scp -i <你的私钥> -r scripts/ root@<新IP>:/root/openvela-build/

# ② 装打包与编译依赖（幂等，可重复跑）
ssh root@<IP> 'bash /root/openvela-build/scripts/install_pack_deps.sh'

# ③ 一键构建（内部会依次：环境自检 → repo sync → 应用全部补丁 → 编译 → 打包）
ssh root@<IP> 'cd /root/openvela-build && bash scripts/remote_build_job.sh start'

# ④ 查看进度（可反复调用）
ssh root@<IP> 'bash /root/openvela-build/scripts/remote_build_job.sh status'

# ⑤ 取回镜像
scp root@<IP>:/root/openvela/vendor/allwinnertech/lichee/out/r528s3/gemini-s1_nand/\
rtos_nuttx_r528s3-gemini-s1_uart0_128Mnand.img ./firmware/
```

**要编带界面的配置**（默认是 `nsh`）：

```bash
ssh root@<IP> 'cd /root/openvela-build && BOARD_CONFIG=configs/nsh_minidisplay \
    bash scripts/remote_build_job.sh start'
```

切换配置时脚本会**自动 `distclean`**（靠 `~/.openvela-build/.last_config` 标记检测），
不需要手工清理。

**一次性需要人工介入的只剩三处**（脚本处理不了）：

| 事项 | 为什么必须人工 |
|---|---|
| `speexdsp` 从 GitHub 下载 | 国内云主机访问 GitHub 实测 90 秒（等于不通）。**可在本机下好后 scp 上去**，见坑 1 |
| Gitee LFS 配额 | 若 `libs_openvela_vela` 的配额也耗尽，需要换源或换账号，见坑 5 |
| 磁盘是否够 | 新实例给足 60GB；不足时用 `MIN_DISK_GB=8`（见坑 2） |

> 其余 10 个坑脚本已全部覆盖（`build_openvela.sh` 第 5.5 步会逐条应用并打印结果）。

## 一、下载类问题

### 坑 1：GitHub 依赖下载超时

**现象**（编译阶段中断）：

```
curl: (56) OpenSSL SSL_read: error:0A000126:SSL routines::unexpected eof while reading
make[3]: *** [Makefile:32: /root/openvela/apps/audioutils/speexdsp/speexdsp] Error 56
```

**诊断**：先看这个依赖从哪来 —— `apps/audioutils/speexdsp/Makefile`：

```makefile
SPEEXDSP_URL ?= "https://github.com/xiph/speexdsp/archive/refs/tags"
$(Q) curl -O -L $(SPEEXDSP_URL)/$(SPEEXDSP_VERSION).zip
```

我们实测过三个源从该云主机的响应时间：**Gitee 0.96s / GitCode 0.81s / GitHub 90.2s**。
90 秒等于不可用，所以 curl 在 1 分半后连接被断。

**修法**：在你**本机**（能通 GitHub）下载，再传上去，解压到 Makefile 期望的路径：

```bash
# 本机
curl -O -L https://github.com/xiph/speexdsp/archive/refs/tags/SpeexDSP-1.2.1.zip
scp SpeexDSP-1.2.1.zip root@<IP>:/root/

# 远端
cd /root/openvela/apps/audioutils/speexdsp
unzip -o /root/SpeexDSP-1.2.1.zip
mv speexdsp-SpeexDSP-1.2.1 speexdsp      # ← 目录名必须是这个
ls speexdsp/libspeexdsp/resample.c       # 验证
```

**关键点**：make 的规则是"目标目录存在就跳过下载"，所以**手工放好即可，无需改 Makefile**。

> **顺带排掉同类风险**：构建前先搜索还有哪些依赖会从 GitHub 拉：
> ```bash
> grep -rn "_URL" --include=Makefile /root/openvela/apps /root/openvela/packages
> ```
> 再对照 defconfig 确认哪些真的被启用。本例中 `CONFIG_AUDIOUTILS_SPEEXDSP=y` 是唯一一个，
> 其余 crypto 库的源码目录都已存在，不会触发下载。

### 坑 5：预编译库是 Git LFS 指针

**现象**（链接阶段）：

```
arm-none-eabi-ld: .../libquickapp.a: file format not recognized; treating as linker script
arm-none-eabi-ld: .../libquickapp.a:1: syntax error
```

**诊断第一步 —— 看文件大小**。回看目录列表时就有异常：

```
-rw-r--r-- 1 root root      134 libgui_wrapper.a     ← 134 字节！
-rw-r--r-- 1 root root      134 libquickapp.a        ← 134 字节！
-rw-r--r-- 1 root root  4306524 libapps_vapp.a       ← 正常
-rw-r--r-- 1 root root 16896792 liblibfeature.a      ← 正常
```

134 字节正是 LFS 指针的大小。看内容确认：

```
version https://git-lfs.github.com/spec/v1
oid sha256:34d2aad207edeccfc795b1fb7e08f329ab84c4f59eabdbd10677f0333d804768
size 108089034
```

**为什么 `git lfs pull` 没用**：仓库里**没有** `.gitattributes` 的 lfs 规则，
所以 git-lfs 不认为这些文件受它管，`git lfs ls-files` 返回 0 条。

**诊断第二步 —— 配额**。直接按 LFS Batch API 协议请求：

```bash
curl -X POST https://gitee.com/open-vela/vendor_openvela.git/info/lfs/objects/batch \
  -H "Accept: application/vnd.git-lfs+json" -H "Content-Type: application/vnd.git-lfs+json" \
  -d '{"operation":"download","transfers":["basic"],"objects":[{"oid":"34d2...","size":108089034}]}'
```

`libquickapp.a` 拿到了下载地址，但 `libgui_wrapper.a` 被拒：

```
507 link object failed, insufficient quota will used/total: 5211.44MB/5120.00MB
```

**Gitee 对该仓库的 LFS 流量配额已用尽。**

**修法的关键一步 —— 换仓库**。源码 `Make.defs` 的注释里写了这批库的出处：

> These are prebuilt static libraries from the **libs_openvela_vela** repository

LFS 的 OID 是**内容哈希**，跨仓库通用。实测：

| 端点 | `libgui_wrapper.a` |
|---|---|
| `vendor_openvela`（Gitee） | ✗ 配额用尽 |
| **`libs_openvela_vela`（Gitee）** | **✓ 可下载** |
| `libs_openvela_vela`（GitHub） | ✓ 可下载 |

于是写成 `scripts/fetch_lfs_libs.py`：多端点逐个尝试 → 下载 → **校验 sha256**。
两个库（103MB + 133MB）都下载并校验通过。

> **可复用的经验**：LFS 拉不到时，先找**同一个 OID 在哪个仓库能取到**，
> 而不是急着放弃或写桩。

## 二、构建系统类问题

### 坑 3：`--whole-archive` 的写法必须跟随链接器（**最容易只修一半**）

**现象**（第一次，`configs/nsh`）：

```
LD: nuttx
arm-none-eabi-ld: unrecognized option '-Wl,--whole-archive'
```

**诊断链**（三步定位到真正来源）：

1. `-Wl,` 是给 **gcc 驱动器**的写法；裸 `ld` 要用不带前缀的 `--whole-archive`
2. 第一嫌疑 `CONFIG_DEBUG_LINK_WHOLE_ARCHIVE` —— 查 `.config`：**未开启**，排除
3. 全树搜 `--whole-archive`，最终在 `nuttx/Make.defs:150` 找到（**它是个符号链接**，
   指向板级共享的 `vendor/allwinnertech/boards/r528/r528s3-gemini-s1/scripts/Make.defs`）：

```makefile
ifeq ($(CONFIG_QUICKAPP),y)
EXTRA_LIBS += -Wl,--whole-archive          ← 问题在这
EXTRA_LIBS += $(QUICKAPP_PREBUILT_DIR)/libapps_vapp.a
...
EXTRA_LIBS += -Wl,--no-whole-archive
endif
```

**第一版修法（只对了一半）**：把它改成裸 `--whole-archive`。`nsh` 编过了。

**但换到 `configs/nsh_minidisplay` 又挂了，而且方向相反**：

```
LD: nuttx
arm-none-eabi-gcc: error: unrecognized command-line option '--whole-archive'
```

**根因**：`LD` 会**随配置切换** —— `nuttx/arch/arm/src/common/Toolchain.defs`：

```makefile
else
    CC      = $(CROSSDEV)gcc
    LD      = $(CROSSDEV)ld            ← 默认裸链接器
    ...
    ifeq ($(CONFIG_LTO_FULL),y)
      ifeq ($(CONFIG_ARM_TOOLCHAIN_GNU_EABI),y)
        LD := $(CROSSDEV)gcc            ← 开了 LTO 就换成 gcc
```

LTO 必须由编译器驱动链接（才能跑 LTO 插件），于是：

| 配置 | `CONFIG_LTO_FULL` | `LD` | 需要的写法 |
|---|---|---|---|
| `configs/nsh` | 未开 | `arm-none-eabi-ld` | `--whole-archive` |
| `configs/nsh_minidisplay` | **=y** | `arm-none-eabi-gcc` | `-Wl,--whole-archive` |

**厂商原文只对上 LTO 那一种；我第一版只对上非 LTO 那一种。两边都是"半对"。**

**正确修法 —— 抄 NuttX 自己的做法**。`nuttx/arch/arm/src/Makefile` 里就是这么判断的：

```makefile
# Override in Make.defs if linker is not 'ld'
ifeq ($(LD),$(CC))
    LDSTARTGROUP ?= -Wl,--start-group
    LDENDGROUP   ?= -Wl,--end-group
else
    LDSTARTGROUP ?= --start-group
    LDENDGROUP   ?= --end-group
endif
```

于是引入同样的判断。**用递归变量（`=`）而不是立即展开**：`EXTRA_LIBS` 本身是递归
变量（已用 `make -p` 确认），所以 `$(QAPP_WL)` 会留到真正链接时才求值 —— 那时 `LD` 已确定：

```makefile
QAPP_WL_IF_GCC = -Wl,
QAPP_WL = $(if $(filter $(LD),$(CC)),$(QAPP_WL_IF_GCC),)

EXTRA_LIBS += $(QAPP_WL)--whole-archive
...
EXTRA_LIBS += $(QAPP_WL)--no-whole-archive
```

已固化为 `scripts/fix_vendor_make_defs.py`（幂等，能收敛厂商原文/各种半对写法）。

> ### ⚠️ 这里还埋着一个 make 陷阱，我踩了
>
> 第一版自适应定义写的是：
>
> ```makefile
> QAPP_WL = $(if $(filter $(LD),$(CC)),-Wl,)      # ← 错的
> ```
>
> 报错信息是 `-Wl--whole-archive` —— **逗号没了**。
> 原因：`$(if 条件,真值,假值)` 是**用逗号分隔参数**的，真值里写的字面逗号被当成了
> 参数分隔符，`-Wl,` 于是变成了 `-Wl`。
> 修法就是把那个逗号放进独立变量（上面的 `QAPP_WL_IF_GCC`）。
>
> **同理还有一层坑**：判断"定义是否已存在"时，不能用 `"QAPP_WL" in text` ——
> 替换后文本里出现的 `$(QAPP_WL)` 是**引用**，也会命中，结果是"引用了却从未定义"。
> 必须匹配 `QAPP_WL =` 这种**定义**形式。我第一次的脚本就因为这个 bug
> 只加了引用没加定义，白跑一轮构建。

> **一般化经验**：厂商/上游脚本里凡是把 gcc 风格标志写进 make 变量的地方，
> 都要先确认**这个工程的链接器到底是哪个**。而链接器可能随配置变
> （LTO、不同 toolchain、`--cmake` 与否），所以**别写死，让它自适应**。

### 坑 6：libswscale 缺失

**现象**：

```
arm-none-eabi-ld: .../liblibmedia.a(media_video_output.c.o):
    undefined reference to `sws_getContext'
    undefined reference to `sws_scale'
    undefined reference to `sws_freeContext'
```

**诊断 —— 确认它到底存不存在**（不要凭经验假设）：

- `find /root/openvela -iname "*swscale*"` → **0 个结果**
- 扫描全树约 **3900 个 `.a`**（`nm --defined-only`）→ **无一定义** `sws_getContext`
- `libs_openvela_vela` 仓库完整文件清单（49 条）→ 也没有

**为什么会报错**：厂商把整批预编译库放在 `--whole-archive ... --no-whole-archive`
之间，这会强制把库里**每一个**目标文件都链进来，包括用不到的视频缩放模块，
于是它引用的 `sws_*` 也必须被满足。

**修法**：`board/patches/swscale_shim.c` —— 提供三个符号以满足链接，
**但不实现功能**：`sws_getContext` 记日志返回 NULL、`sws_scale` 返回 -1、`sws_freeContext` 空实现。

设计取向是**响亮失败**而非静默糊弄：真走到视频缩放路径时，日志里会有明确报错。

**代价（必须如实说明）**：本固件的**视频缩放能力不可用**。
本项目目标是音频采集/播放与语音后端，不经过该路径，因此无影响。
需要真库时：交叉编译 FFmpeg 的 libswscale → 放进厂商库目录 →
从 `src/Makefile` 的 `CSRCS` 移除 `swscale_shim.c` 并把该库加进 `EXTRA_LIBS`。

### 坑 7：shim 自身的编译错误（一个很好的教训）

**现象**：

```
In file included from .../nuttx/include/sys/time.h:33, from swscale_shim.c:53:
.../nuttx/include/sys/select.h:87:16: error: 'OPEN_MAX' undeclared here (not in a function)
.../nuttx/include/nuttx/wdog.h:339:15: error: 'CLOCK_MAX' undeclared
```

**误导点**：同目录的 `r528_bringup.c` **也** `#include <syslog.h>`，却能编译。
所以一开始以为是"包含顺序"。

**踩到的陷阱 —— 单独探测给出了错误结论**：写了 `scripts/probe_headers.sh`，
把 6 种头文件组合拿编译器单独编，**全部通过**（包括与出错文件一模一样的组合）。
也就是说：**这个问题无法用单独编译来复现或预测**，只有在完整构建的包含路径下才暴露。

**修法 —— 对齐已被证明可行的文件**：`shim_binary_compat.c` 只包含
`nuttx/config.h + stddef.h + stdint.h`，在真实构建里稳定通过。
于是严格照抄这三个，并把用到的日志接口就地声明：

```c
#include <nuttx/config.h>
#include <stddef.h>
#include <stdint.h>

extern int syslog(int priority, const char *format, ...);
#define SHIM_LOG_ERR 3      /* POSIX LOG_ERR */
```

> **经验**：改不动就**对齐同目录里已经能编译的文件**，比推理头文件依赖更快更可靠。

## 三、工具与环境类问题

### 坑 4：`pkill` 把执行它的 shell 自己杀了

**现象**：发一条"先停旧任务、再启动新任务"的命令，ssh **返回空输出**，新任务没启动，
而旧日志还在。

**根因**：

```bash
pkill -f build_openvela     # ← 这个模式也匹配到"正在执行这行命令的 shell"！
```

shell 的命令行里就含 `build_openvela` 这个字符串，于是它把自己杀了，
后面的启动命令根本没执行。

**修法**：正则里用字符类打断自匹配：

```bash
pkill -f "build_openve[l]a"
```

`build_openve[l]a` 匹配 `build_openvela`，而 shell 自身命令行里是
`build_openve[l]a`（带方括号），**不匹配**，于是安全。

> 这个坑最阴的地方是**它静默失败**：没有报错，只是"什么都没发生"。

### 坑 8：kconfig-frontends 不在 manifest 里

**现象**：

```
tools/scripts/envsetup.sh: line 157:
    pushd: /root/openvela/prebuilts/kconfig-frontends: No such file or directory
```

**诊断**：看那段代码的逻辑：

```bash
if [ ! -f "${ROOTDIR}/prebuilts/kconfig-frontends/bin/kconfig-conf" ] &&
   [ ! -x "$(command -v kconfig-conf)" ]; then
    pushd ${ROOTDIR}/prebuilts/kconfig-frontends
    ./configure --prefix=... && make install
fi
```

**只要系统里已有 `kconfig-conf`，这段就完全不会执行。**

**修法**：它不在 openvela manifest 里，但是 Ubuntu 的普通软件包：

```bash
apt-get install -y kconfig-frontends      # 提供 /usr/bin/kconfig-conf
```

### 坑 9：第三方脚本 + 我方 `set -u`

**现象**：

```
tools/scripts/envsetup.sh: line 72: XTENSAD_LICENSE_FILE: unbound variable
```

**根因**：我的脚本开头是 `set -euo pipefail`（最严格），而 lichee 的脚本是按
"人工在 bash 里敲"写的，会引用未定义变量。`source` 之后严格模式**同样生效**，
于是在第一处未定义变量上直接中止。

**修法**：整段放进**子 shell** 并临时关掉严格模式 —— 既让第三方脚本按它假设的环境跑，
又不让它的副作用（`cd`、`export`、函数定义）泄漏回主脚本：

```bash
PACK_RC=0
set +e                      # 必须：pipefail 下失败的管道会让 set -e 终止整个脚本
(
    set +u
    set +e
    cd "$LICHEE_DIR" || exit 1
    source ./envsetup.sh
    lunch_nuttx r528s3-gemini-s1
    pack
) 2>&1 | tee -a "$LOG_FILE"
PACK_RC=${PIPESTATUS[0]}
set -e
```

### 坑 10：菜单编号猜错（应当直接传项目名）

**现象**：打包只打印一句就退出，没有任何产物：

```
platform(%%_*) not support
```

**根因**：`lunch_nuttx` 是交互式菜单，我按 README 猜了 `2`。实际菜单是：

```
1. r528s3-dshanpi
2. r528s3-evb4          ← 我喂的 "2"，选错了
3. r528s3-gemini-s1     ← 本板
4. r528s3-velaevb1
```

**修法**：看它的实现，**支持直接传项目名**，不走菜单：

```bash
function lunch_nuttx() {
    if [ "$1" ] ; then select=$1          # 有参数就直接用
    else print_lunch_menu; read select; fi   # 否则交互
```

于是改成 `lunch_nuttx r528s3-gemini-s1` —— 比编号**可靠且自解释**。

### 坑 11：`dragon: No such file or directory`（文件其实在）

**现象**：

```
pack_img.sh: line 1001: .../lichee/tools/tool/dragon: No such file or directory
```

**但这个文件明明存在**：

```
-rwxr-xr-x 1 root root 137891 dragon      ← 有，且有可执行权限
```

**诊断**：`ls` 有、执行却报"文件不存在"，这是 **ENOENT 的经典伪装** ——
真正缺的是**动态加载器/依赖库**。查 ELF 头：

```
Class:   ELF32
Machine: Intel 80386        ← 32 位 x86！
```

而系统是 x86_64 Ubuntu 且未装 i386 运行库 → `execve` 返回 ENOENT → shell 报成"文件不存在"。

**修法**：`scripts/install_pack_deps.sh` 里固化：

```bash
dpkg --add-architecture i386 && apt-get update
apt-get install -y libc6:i386 libstdc++6:i386 libgcc-s1:i386 lib32z1
```

> 装完 `libc6:i386` 后错误会**变成**缺 `libstdc++.so.6`（dragon 是 C++ 写的），
> 所以这几个包要一起装，别一个个试。

## 四、方法论：两条"别信表层信号"的教训

### 坑 12：`pack` 的返回码**两个方向都不可信**

| 情况 | pack 返回码 | 实际结果 |
|---|---|---|
| 选错板型 | **0** | ❌ 什么都没打包（假成功） |
| 打包成功 | **1** | ✅ 镜像已生成（假失败） |

**修法 —— 一律以产物为准**：

```bash
PACK_IMG="$(find "$LICHEE_DIR" -maxdepth 4 -type f -name '*.img' \
            -newermt '-30 minutes' 2>/dev/null | head -1)"
if [[ -n "$PACK_IMG" ]]; then
    ok "打包完成：$PACK_IMG"
else
    warn "打包未产出镜像"
fi
```

> 我在两个方向上都吃过亏：先是假成功骗过了第一版脚本，
> 改成"要求返回码 0 且产物存在"之后，又被假失败误报了一次。
> **最终判定只看产物。**

### 坑 13：日志中文乱码

拉回本地分析时不要忘了指定编码，否则 UTF-8 会被按 GBK 解出乱码、
连 `Select-String "第 7 步"` 都匹配不到：

```powershell

## 五、一条更省事的路径（ssh 内联引号的坑）

本次有大量时间花在 **ssh 内联命令的引号**上。PowerShell → ssh → bash 三层引号叠加，
`|`、`()`、`&&` 都容易被本地 shell 提前吃掉，表现为各种离奇的
`syntax error near unexpected token`。

**结论：不要拼一行内联命令，把逻辑写进脚本文件再执行。**

因此留下这几个小工具：

| 脚本 | 用途 |
|---|---|
| `remote_build_job.sh` | 远端构建的 start / stop / status（含防自杀的 pkill 写法） |
| `install_pack_deps.sh` | 补齐打包依赖（kconfig-conf + 32 位运行库） |
| `fetch_lfs_libs.py` | 多端点补 LFS 库并校验 sha256 |
| `find_symbol.py` | 全树扫描符号定义（判断"某个库到底有没有"） |
| `probe_headers.sh` | 头文件组合探测（注意：结论可能不代表完整构建） |

日志分析也尽量**拉回本地**再用 PowerShell/Python 处理，比在远端 grep 稳妥。

## 七、烧录前需要知道的三件事

1. **这会替换整个固件。** 出厂固件跑的是图形启动器（`luncher_mini`），
   而我们编的是 `nsh` 配置（纯命令行）。烧录后**图形界面会消失**。
   如需保留，应改编 `configs/nsh_minidisplay`（该配置同样存在）。
2. **本固件的视频缩放不可用**（坑 6 的 shim 所致）。音频与语音后端不受影响。
3. **`BoardConfig.mk` 里写的是 `sun8iw20p1_velaevb1_rtos_nand`**，镜像名含 `128Mnand`。
   这是厂商 `gemini-s1_nand` 配置目录自带的取值（启动引导复用 velaevb1），
   属于原样配置，未被我改动 —— 但烧录前你应当知道这一点。

**烧录不上/异常时的退路**：板子可按 FEL 键进入 BROM 模式，用 PhoenixSuit 重烧原厂固件恢复。
