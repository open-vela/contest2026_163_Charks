# 闭环 v2 设计 —— 让演示效果"看得见、听得清、跑得稳"

> 2026-09-20。起因：v1 闭环在演示场景下不稳、反馈弱。
> 本文先记录**为什么 v1 会失败**（都有实测依据），再给出 v2 的分层设计与状态机。

---

## 一、v1 为什么在演示时崩（四个结构性原因）

| # | 原因 | 实测依据 | 后果 |
|---|---|---|---|
| 1 | **麦克风输入通路开机默认全 Off，且只有百度后端会打开它** | `board/baidu_voice/README.md` §5.0；`mic_route_enable()` 全项目唯一调用点是 `baidu_asr.c:358` | 用火山后端时录音必败，报误导性的 `capture only support 1~3 channel` |
| 2 | **换网络环境后 BSSID 被钉死** | `探板记录表.md` §3.1 坑 2 | 现场换 WiFi → 扫描看到 AP 却报 `No Assoc Network After Scan Done` |
| 3 | **开机时 WiFi 固件下载偶发失败** | `探板记录表.md` §3.1 坑 1（`status=0x27`） | 刚上电就演示，WiFi 可能是坏的，整条云链路断 |
| 4 | **视觉反馈押在未验证的屏幕上** | r7–r12 六轮迭代无任何结论 | 屏幕白屏时，演示看起来像"什么都没发生" |

外加两个体验问题：

- **ADC 数字增益厂商默认 160，比可用点低约 20 dB** → 录音太轻 → ASR 识别率被拖垮（`探板记录表.md` §6.2.1）
- **板上 nsh 有四条硬约束**（无变量赋值、无 grep、引号不可靠、证书不信任）→ 任何"多步骤带状态"的脚本放板上都不可靠

> **v1 的共同病根：把"一次性演示"当成"调试好的环境"在跑。**
> v2 的设计原则就是**为一次性执行而设计**。

## 二、v2 的核心决策

### 决策 1：编排逻辑放 PC 侧，板子只执行单条命令

```
        PC 侧 demo_loop.py（编排者）
        ├─ 状态机 / 超时 / 重试 / 日志 / 降级
        └─ adb shell 逐条下发 ──────────▶  板子（执行者）
                                         只做单条命令：
                                         录音、播放、RGB、表情
```

**为什么**：彻底绕开 nsh 的四条硬约束，同时获得超时控制与失败重试——这两样正是演示稳定性的关键。

**代价**：板子的"自主性"下降。因此 v2 保留 `--voice board` 开关，
把 ASR/TTS 切回板端 AI Agent 通道，用于展示"板子自己在思考"。

### 决策 2：三层反馈，RGB 兜底

| 通道 | 听 listening | 想 thinking | 说 speaking | 依赖 |
|---|---|---|---|---|
| 声音 | — | — | TTS 播放 | 扬声器（R4 已验证） |
| 表情 | 睁大眼 | 眼动+脸红 | 嘴开合 | 屏幕（**未验证**） |
| **RGB 灯** | 蓝呼吸 | 紫快闪 | 绿渐变 | 仅 `rgb_led` 命令（**已确认存在**） |

**关键**：RGB 层**由 PC 经 adb 驱动，不需要改 C 代码、不需要编译**。
所以即使屏幕最终是白屏，演示依然有强烈的状态反馈。

### 决策 3：LLM 用 StepFun，语音层可插拔

- LLM → `https://api.stepfun.com/step_plan/v1`（国内直连，延迟远比境外 Cloudflare 稳）
- ASR / TTS → **设计为可插拔**，两套实现：
  - `pc`：PC 侧直连（最快见效、最好调试）
  - `board`：板端 AI Agent 的 voice 通道（展示板端自主）
- ⚠️ **StepFun 是否有 ASR/TTS 待确认**（联网检索工具在当前环境不可用）。
  若没有，ASR/TTS 保留百度（免费 5 万次永久，代码已就绪且 93 项测试通过）。

### 决策 4：麦克风通路改为后端无关（需编译）

把 `mic_route_enable()` 从 `baidu_asr_init_ops()` 挪到 `voice_channel_init()`。

**这是 v1 病根 1 的正解**：`mic_route.c` 自己的注释就写了它是"板级代码，不是百度专属"，
但实际只被百度调用。挪位之后任何后端、包括火山，都能自动打开通路并设好 205 增益。

## 三、状态机

```
                    ┌──────────────┐
                    │   IDLE 待机   │ ◀──────────────┐
                    │  青白微光      │                │
                    └──────┬───────┘                │
                    按键/自动开始                    │
                           ▼                        │
   ┌────────────────── LISTENING 聆听 ──────────────┤
   │  蓝呼吸 · 睁大眼 · arecord 5s                   │
   └──────┬──────────────────────────────────────────┘
          │ 录音完成                                  │
          ▼                                          │
   ┌────────────────── THINKING 思考 ───────────────┤
   │  紫快闪 · 眼动 · ASR → LLM                     │
   └──────┬──────────────────────────────────────────┘
          │ 拿到回复文本                              │
          ▼                                          │
   ┌────────────────── SPEAKING 说话 ───────────────┤
   │  绿渐变 · 嘴开合 · TTS → aplay                  │
   └──────┬──────────────────────────────────────────┘
          │ 播放结束                                  │
          └──────────────────────────────────────────┘
```

**异常分支**（v1 完全缺失，v2 必须有）：

| 异常 | RGB 表现 | 处理 |
|---|---|---|
| WiFi 未连 | 红色快闪 | 自动重连 + 清 BSSID，重试 2 次 |
| 录音失败 | 红色快闪 | 自动重发 amixer 使能，重试 1 次 |
| ASR 无结果 | 黄色慢闪 | 用兜底话术进 SPEAKING（不当机） |
| LLM 超时 | 黄色慢闪 | 重试 1 次，再失败走兜底话术 |
| TTS 失败 | 红色快闪 | 跳过播放，仅表情+RGB 反馈 |

> **兜底话术**来自 `prototype/safety.py` 的四种动作设计，
> 即使全链路挂掉，演示也不会冷场。

## 四、准备阶段（演示前一次跑完，对应 v1 病根 2/3）

```
1. WiFi 保活     wapi reconnect wlan0          ← 治病根 3（开机 FW 下载偶发失败）
2. 清 BSSID      wapi ap wlan0 00:00:...:00    ← 治病根 2（换网络必死）
3. 取 IP          renew wlan0
4. 验时钟         date                          ← 1970 则告警（HTTPS 会受影响）
5. 开麦克风       amixer（3 路开关 + 增益 205）  ← 治病根 1 的运行时兜底
6. 探测反馈通道    rgb_led / 表情命令是否存在
7. 选后端         board 或 pc
```

**第 5 步是运行时兜底**：即使 C 层重构后，`amixer` 也不持久化（每次开机失效），
所以准备阶段每次演示都要重发一遍，双保险。

## 六、怎么跑

```powershell
# 0. 配密钥（config.yaml 已被 .gitignore，不会提交）
cd prototype
copy config.example.yaml config.yaml
# 编辑 config.yaml：
#   llm.api_key      <- StepFun 的 key
#   baidu.api_key / baidu.secret_key  <- ASR/TTS 用（StepFun 若无语音则保留百度）

# 1. 准备 + 探测板端参数（先不带 --gain-numid 跑一次，看它提示什么）
cd ..
py -3.13 tools/demo_loop.py prepare

#    板端敲 `adb shell amixer` 查到 ADC 数字增益的编号后，补上：
py -3.13 tools/demo_loop.py prepare --gain-numid <编号>

#    prepare 还会探测 rgb_led / 表情命令，把推测到的用法分别用
#    --rgb-template "..." 与 --face-cmd "..." 传进去

# 2. 单轮（对着日志调 prompt 与音频链路）
py -3.13 tools/demo_loop.py once --gain-numid <编号>

# 3. 循环演示
py -3.13 tools/demo_loop.py run --rounds 10 --gain-numid <编号>
```

> ⚠️ 本机请用 `py -3.13`：`C:\msys64\mingw64\bin\python.exe` 没有 pip。
> ⚠️ `rgb_led` 的确切命令形式**未经实测**，prepare 阶段只是探测，必要时用
> `--rgb-template` 显式指定（模板支持 `{r}` `{g}` `{b}`）。

## 七、验证标准（v2 验收）

- [ ] 上电后**一条命令**完成准备，无需人工敲 amixer / wapi
- [ ] 说话→**50ms 内** RGB 变蓝、表情变"聆听"（反馈要先于结果）
- [ ] 思考阶段有可见反馈，不是静默等待
- [ ] ASR 结果正确显示（先验识别、再验交互）
- [ ] 全程**无冷场**：任何一环失败都有兜底话术
- [ ] 连续跑 5 轮不崩
- [ ] 换一个 WiFi 环境后，重跑仍成功（病根 2 回归测试）
