**连通性实测**：

| 测试 | 结果 |
|---|---|
| `ping -c 2 10.0.0.1` | ❌ `ERROR: sendto failed at seqno 0: 101`（ENETUNREACH）；2 packets transmitted, 0 received |

### 2.9 启动脚本（发现固件缺陷）

**`/etc/init.d/rcS` 全文（共 25 行，逐字）**：

```sh
set +e
set -x
echo "You're running an nsh image."
mount -t romfs /dev/res /resource
mount -t yaffs /dev/usrdata /data
set errcode $?
if [ $errcode -ne 0 ]
then
  echo "/dev/usrdata mount failed, errcode is" $errcode
fi
adbd &
set resetcause `resetcause`
echo $resetcause
if [ "$resetcause" == "cpu_soft_reset(restore)" ]
then
  echo "recovery reset system"
  sh /etc/factory.sh
  echo "reboot system now"
  reboot
fi
echo "Starting bluetoothd..."
bluetoothd &
ntpcstart &
if [ -f /data/etc/wifi/wapi.conf ]
then
```

**⚠️ 文件在 `then` 之后就没有内容了，也没有 `fi`** —— 这是一个**残缺的脚本**。

**结论**：

- `adbd &` 在这里启动 → **这解释了为什么 ADB 可用**
- `bluetoothd &`、`ntpcstart &` 启动
- **WiFi 段落的 body 缺失** → `start_wifi.sh` **从未被调用**，这是 WiFi 不通的直接原因之一
- 出厂固件自身存在缺陷，**不应作为长期使用的固件**，应当自己编译烧录

### 3.2 `wapi` 命令在固件里不存在

- `help` 的 Builtin Apps 里**没有 `wapi`**，只有 `test_wifi` 和 `adapter_test`
- 但 `start_wifi.sh` 通篇使用 `wapi disconnect` / `wapi essid` / `wapi psk` / `wapi reconnect` 等

**可能原因**：`wapi` 未编入该固件配置（虽然板级 defconfig 里有 `CONFIG_WIRELESS_WAPI_CMDTOOL=y`，
但出厂固件用的是 `trunk` 分支且配置可能不同）。

**要做的事**：实测 `test_wifi` 的用法，或确认 `wapi` 是否以其他路径存在。
实在不行，**自己编译时确保 `CONFIG_WIRELESS_WAPI_CMDTOOL=y` 生效**。

### 3.4 关于 NAND 容量（**仍无法确定，但不阻塞**）

已核实的三种说法互相冲突：

| 来源 | 说法 |
|---|---|
| `图2.png` 参数表 | NAND **256MB** |
| 官方 `sys_partition.fex` 的 `dummy_1`（出厂值同为 262144） | 该行注释称"表示 flash 总容量（如 524288 = 256MB）"→ 262144 = **128MB** |
| 出厂固件分区表实测 | 正数分区合计 788,480 扇区（≈385 MB），另有 `UDISK = -528128`（负值语义未知） |
| 参考项目 `dhy-dh/openvela-smartband-gemini-s1` | Gemini-S1 是 **128 MiB**，镜像名带 `128Mnand`；DshanPi 才是 256 MiB |

**判断**：静态文件与运行时数据都**无法给出确定容量**（`sys_config.fex` 里 `storage_type = -1` 是 auto scan）。

**行动**：容量**不影响动手**。稳妥做法：

1. 用 `gemini-s1_nand` 打包目标（**不要用 dshanpi**）
2. 烧镜像名含 `gemini-s1` 的固件（**不要烧含 `256Mnand` 的**）
3. 启动日志里找 NAND 容量打印行确认
4. 板子上 NAND 芯片丝印也可直接看

### 6.5 采集实测 —— 根因与修复

#### 首次失败

```
[SND_ERR][sunxi_codec_hw_params:1250] capture only support 1~3 channel
[SND_ERR][soc_pcm_hw_params:423]      codec_dai set hw params failed
```

#### 排查：报错信息与真实原因不符

`-c 1` / `-c 2` / `-c 3` / 默认 **全部报同一个错** → 与声道数无关。

驱动源码 `chips/r528/drivers/rtos-hal/hal/source/sound/codecs/sun8iw20-codec.c:1250`：

```c
} else {                                  /* 采集方向 */
    if (sunxi_get_adc_ch(codec) < 0) {
        snd_err("capture only support 1~3 channel\n");   /* 消息写错了 */
        return -EINVAL;
    }
```

`sunxi_get_adc_ch()` 读 codec 模拟寄存器判断哪条输入通路使能
（`MIC_PGA_EN` / `FMINL_EN` / `LINEINL_EN`），
全都没使能就返回 −1。

#### 混音器全表（`amixer`，关键项）

```
numid=5,  'DAC digital volume switch'        value=On    ← 播放能用就靠它
numid=17, 'ADC1_2 digital volume switch'     value=Off   ← 需打开
numid=18, 'ADC3 digital volume switch'       value=Off
numid=25, 'MIC1 input switch'                value=Off   ← 需打开
numid=28, 'MIC2 input switch'                value=Off   ← 需打开
numid=31, 'MIC3 input switch'                value=Off
numid=26/29, 'FM input L/R switch'           value=Off
numid=27/30, 'LINE input L/R switch'         value=Off
numid=8/9/10,  'MIC1/2/3 gain volume'        value=31（最大）
numid=22/23/24,'MIC1/2/3 input select'       value=MIC_DIFFER
numid=32, 'Playback audio route'             value=lo+hp+spk
```

**输入开关全部为 `Off`** —— 这就是根因。

#### 修复

```bash
amixer set 25 1     # MIC1 input switch            Off -> On
amixer set 28 1     # MIC2 input switch            Off -> On
amixer set 17 1     # ADC1_2 digital volume switch Off -> On
```

修复后采集立刻成功，`SND_ERR` 消失。

### 6.6 ⚠️ 混音器设置**不持久化**（完整复现链）

| 步骤 | 操作 | 结果 |
|---|---|---|
| 1 | `reboot` 后直接 `arecord` | ❌ 失败，文件未生成 |
| 2 | `amixer get 25` | `value=Off` |
| 3 | `amixer set 25/28/17 1` | `value=On` |
| 4 | 再次 `arecord -d 2` | ✅ 成功，64044 字节 |
| 5 | `analyze_wav.py` 体检 | ✅ 可用，峰值 −32.7 dBFS，非零 99.7% |

`resetcause` = `cpu_soft_reset(reboot)`，`uptime` = 0:00，确认是全新启动。

**结论：任何采集程序都必须在打开采集设备前先开混音器通路。**
详见《风险击穿手册.md》5.2.3 与 `board/baidu_voice/README.md` 5.0。

### 6.7 录音文件验证

`arecord -r 16000 -f 16 -c 1 -d 3 /data/r4_rec.wav` → **96044 字节**

尺寸校验：`16000 × 2 × 3 + 44 = 96044` ✓ 精确吻合。

WAV 头解析：

RMS 偏低属正常——当时无人说话，录到的是环境底噪。

### 6.8 内存复核：**906 MB，与参数表严重不符**

### 6.9 顺带发现

| 发现 | 说明 |
|---|---|
| **`dmesg` 持久化在 NAND** | 跨复位保留，是板端实验最有价值的诊断手段 |
| **`resetcause`** | 区分 `power_on` / `cpu_soft_reset(reboot)` / 看门狗。排查"板子莫名重启"第一条命令 |
| **`ps` / `free` / `uptime` / `dumpstack` / `df`** | 均为 nsh 内置（不在 Builtin Apps 列表里） |
| `ls` 不支持通配符 | `ls /data/*.wav` 报 `too many arguments`，要直接 `ls /data` |
| 板端无 `grep` / `tail` | 需要过滤时把 `dmesg` 拉回 PC 处理 |
| **出厂自启动 LVGL 界面** | `luncher_mini`（PID 48）常驻，占着显示；持续报 SHTC3 温湿度 I2C 失败 |
| 前次失联原因 | `resetcause` 为 `power_on(0)`，即**手动断电**——说明当时是**挂死**而非崩溃自动重启。**做板端实验前应接 USB-TTL 串口做保险** |
| 厂商仓库有大量可复用 app | `apps/audio_test`（音频测试，未编入固件）、`apps/xiaozhi_gui`（小智 AI 语音助手！）、`wifi_manager`、`led_rgb`、`led_key`、`ltr553`、`shtc3` 等 |
