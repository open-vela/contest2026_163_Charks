### 上板排查实录：四个坑（按踩到的顺序）

这一轮上板**没有一个坑是"协议写错了"** —— 全是环境/配置/时序问题。
记下来是因为它们各自的**报错都指向错误的方向**。

**① 板子上有一份写死别的 AP 的 WiFi 配置。**
`/data/etc/wifi/wapi.conf`（`ssid "Rivotek-Visitor"`、`bssid "be:c1:a6:ff:d6:5e"`）
**在打包素材里**，每次刷机都回来，且**优先于编译期配置**。
驱动一直去连那个不存在的 AP。现象是"WiFi 配了却连不上"。

**② netinit 的 DHCP 跑在关联完成之前。**
[`netinit_associate.c`](file:///root/openvela/apps/netutils/netinit/netinit_associate.c) 里
`wpa_driver_wext_associate()` 之后**直接 return，不等链路建立**；
而 Realtek 驱动是**异步**关联的。那一轮 DHCP 必然失败。
而应用侧守卫原来**试 12 次（约 1 分钟）就退出**，等驱动真正就绪时它早就走了 ——
**永远不会有人补一次 DHCP**。已改成永不放弃 + 掉线后重新接管。

**③ `CONFIG_NETUTILS_NTPCLIENT_SERVERIP` 是个"静默失效"的配置项。**
它的 Kconfig 是 `depends on !LIBC_NETDB`，而板子**开了 DNS**，
所以这一项**根本不存在** —— 往里写的 IP 被 kconfig 悄悄丢掉，零提示。
实际生效的是默认值 `0.pool.ntp.org;1.pool.ntp.org;2.pool.ntp.org`（国内基本连不上）。
真机 `ps` 里能直接看到：`NTP_daemon 0.pool.ntp.org;1.pool.ntp.org;2.pool.ntp.org`。

**④ 校园网封了出站 UDP 123。**
就算换成阿里云 NTP（203.107.6.88）也拿不到样本。
但 **TCP 完全可用** —— 所以时间同步改用 **HTTP 响应头的 `Date:` 字段**
（任何响应都带，哪怕 301/404/门户劫持页），见 `sc_time.c`。

> **共同教训**：这四个坑的报错分别是
> "连不上 WiFi"、"DHCP 超时"、"NTP 0 样本"、"证书还没生效"——
> **没有一个指向真实原因**。而最后那个最误导：
> `certificate validity starts in the future` 看起来像**证书本身有问题**，
> 会让人去查证书、查服务器，实际只是**板子以为是 1970 年**（没有 RTC）。

### 表情卡顿：自己写的代码触发了整屏重绘

`sc_face.c::bg_from_mood()` 原来按心情**连续**取背景色（19 档 × 22 档），
每变一档就 `lv_obj_set_style_bg_color(f->root, ...)` ——
而 `root` 铺满整屏，**每次都触发整屏重绘**（320×240×2 = 150KB 全推 SPI），
帧预算只有 60ms，于是偶发掉帧。

症状是"**一卡一卡的**"（偶尔卡一下），很容易被误判成 CPU 不够或屏不行。
已改为**量化到 5 档 + 只在档位变化时才调 LVGL**。

同时在 `sc_main.c::ui_loop()` 里加了**常驻**埋点，把一帧拆成
「设属性」和「渲染刷屏」两段分别计时 —— 这两段慢的修法完全相反
（前者是 CPU 竞争，后者是重绘面积太大）。这类问题以后还会遇到，留着比每次重加划算。

> 相关配置事实：`.config` **没有 `CONFIG_SCHED_RR`**（同优先级纯 FIFO，不互相抢占），
> 而 `superchild`(UI)/rt/cap/play/`luncher_mini` **全是优先级 100**；
> 且 `CONFIG_LV_DRAW_SW_COMPLEX=y`（旋转/缩放表情走软件变换，LVGL 里最贵的一段）。

### 一个会骗人的检查方法

用 `strings <img> | grep 中文` 检查中文日志串，会得到**假的 0** ——
`strings` 默认只输出可打印 ASCII，中文（UTF-8 多字节）被整段丢掉。
**必须直接对原始二进制 `grep -a`。**
本项目已经因此在"改动到底编进去没有"上白绕了一圈。

> ### ⚠️ WiFi 是"开机即对话"的最后一环
>
> 板子的开机联网脚本（`rcS.nsh` → `start_wifi.sh`）**两处都断**：
> ① `/data/etc/wifi/wapi.conf` 不在打包素材里，`if [ -f ]` 为假，脚本不执行；

## 四、板端 4 条硬约束（9/19 Agnes 实测发现，写脚本必读）

来自 `tmp/agnes_test_result.txt`，全部实测：

1. **板上的 `sh` 就是 nsh，不支持变量赋值。**
   `sh script.sh` → `nsh: LOG=/data/xxx: command not found`。
   任何含 `VAR=` 或 `$(...)` 的脚本必挂。⚠️ **开机 `start_wifi.sh` 就是这么死的。**

2. **板上没有 `grep` 命令** —— 靠 grep 解析配置的脚本全部失效。

3. **nsh 的引号处理不可靠。**
   `-H "Authorization: Bearer KEY"` 直接传会被拆碎。
   **对策：用 `curl -K <配置文件>` 传参**，绕开所有引号问题。

4. **HTTPS 证书链不被信任**（`curl: (60) BADCERT_NOT_TRUSTED`）。
   临时用 `insecure`（等同 `-k`）；产品化必须把 CA 装进板子。

### 复现模板（板端可直接用）

```sh
# /data/chat.curlconf
url = "https://apihub.agnes-ai.com/v1/chat/completions"
header = "Authorization: Bearer <KEY>"
header = "Content-Type: application/json"
data = "@/data/chat_req.json"
output = "/data/chat_resp.txt"
silent
show-error
insecure
max-time = 30

# 执行
curl -K /data/chat.curlconf
```

## 五、Agnes LLM 接入的实测性能（9/19 22:16）

| 指标 | 每次新建连接 | **连接复用** |
|---|---|---|
| 首字延迟 | 1.9s ~ 10.6s ❌ | **0.81s** ✅ |
| TLS 握手 | 1.06 ~ 10.60s | **0** |
| 流式吐字 | 48 chunk / 约 60 字 / 0.62s | 同 |

**结论：瓶颈不在板子算力，是每次请求重做 TLS 握手。**
板子自身 TLS 只要 0.15s（对 `www.baidu.com`）；到 Agnes 的 Cloudflare 节点
RTT 228ms 且有丢包，证书链 3–5KB 要分多个 TCP 段传，于是抖到秒级。

**服务端真实首字 ≈ 0.55s**（两种算法互相印证）。
→ **实现时必须保持 HTTP 长连接**，否则交互体验不可接受。

## 十一、闭环 v2 —— 已定位根因并重建设计（2026-09-20）

起因：v1 闭环**在演示场景下不稳、反馈弱**（用户实测）。

### 11.1 根因：麦克风采集通路只被百度后端打开

`mic_route_enable()` 全项目**唯一调用点**是 [baidu_asr.c:358](board/baidu_voice/baidu_asr.c) 的
`baidu_asr_init_ops()`（ASR 后端的 `.init` 钩子）。

而 [mic_route.h](board/baidu_voice/mic_route.h) 的头注释写明了：板子**每次开机后混音器
麦克风输入开关默认全是 `Off`，且不持久化**。于是：

| 用的 ASR 后端 | 谁打开通路 | 录音结果 |
|---|---|---|
| `set_voice_asr baidu` | baidu 的 `.init` → `mic_route_enable()` | ✅ |
| `set_voice_asr volcengine`（**AI Agent 默认**） | **没人管** | ❌ 必败 |

失败时报的是驱动那条**与真实原因完全不符**的错：

```
[SND_ERR][sunxi_codec_hw_params:1250] capture only support 1~3 channel
```

**别去调声道数**（`-c 1/2/3` 报同一个错）。真相是驱动 `sunxi_get_adc_ch()`
发现没有任何输入通路使能而返回 −1，只是消息写错了。
`mic_route.c` 自己也说它是"**板级代码，不是百度专属**"——这就是缺陷所在。

### 11.2 v2 已交付

| 文件 | 作用 | 需编译 |
|---|---|---|
| [`设计-闭环v2.md`](设计-闭环v2.md) | 四个崩因、四项核心决策、状态机、验收标准 | — |
| [`tools/demo_loop.py`](tools/demo_loop.py) | 编排器：准备 + 交互循环 + 三层反馈 + 异常降级 | ❌ |
| [`scripts/fix_mic_route_scope.sh`](scripts/fix_mic_route_scope.sh) | 把 `mic_route_enable()` 挪到 `voice_channel_init()`（幂等） | ✅ |
| [`prototype/llm.py`](prototype/llm.py) | 新增 `llm.*` 通用配置段，回退兼容 `deepseek.*` | ❌ |
| [`prototype/config.example.yaml`](prototype/config.example.yaml) | LLM 段改指向 StepFun | ❌ |

**核心思路**：编排逻辑放 PC 侧（绕开 nsh 四条硬约束），板子只执行单条命令；
反馈分三层（声音 / 表情 / **RGB 灯**），RGB 由 PC 经 adb 驱动、**不需要改 C 代码**，
所以即使屏幕最终白屏，演示仍有强烈状态反馈。
