## 一、一句话

**板子开机即进入表情界面，自己直连 StepFun Realtime 对话，不需要电脑、不需要网关。**

```
┌────────────────────────────────────────────────────────────────┐
│ 板子（openvela / R528 / 917MB DDR）                             │
│   superchild 应用（独立任务，开机自启）                          │
│                                                                 │
│   sc_rt      编排：闸门 / 音频泵 / 重连 / 心情推进 / 界面投递     │
│   sc_tls     TLS 1.2（内嵌 DigiCert Global Root G2，只信这一张）  │
│   sc_ws      WebSocket 客户端（自己写，300 行）                   │
│   sc_stepfun 会话协议（session.update / append / delta / 打断）   │
│   sc_resamp  16k ⇄ 24k 定点重采样（多相 FIR + Blackman）          │
│   sc_b64     Base64                                             │
│   sc_emo     情绪判定（emotion.py 的 C 移植，规则表逐条对齐）      │
│   sc_safety  儿童安全（safety.py 的 C 移植，6 类规则）            │
│   sc_key     API Key —— **从 /data 读，不进固件**                │
│   sc_face    24 表情 + 10 维可调 + 心情状态机                     │
│   sc_audio    16k 采集/播放 + 环形缓冲                           │
└───────────────────────────┬────────────────────────────────────┘
                            │ wss://api.stepfun.com/v1/realtime?model=...
                            │ 24000 Hz / PCM16 / 单向 TLS
                    StepAudio 3 Realtime
```

**ECS 上的网关不再需要。** 它原来做的四件事全部下沉：

| 原来在网关 | 现在在板子 |
|---|---|
| Python + `websockets` 库 | `sc_ws.c`（自写）+ `sc_tls.c`（mbedtls） |
| `wss://` 靠系统 CA | 内嵌单张根证书，`VERIFY_REQUIRED` |
| `resample.py`（numpy） | `sc_resamp.c`（定点，同一套算法） |
| `emotion.py` / `safety.py` | `sc_emo.c` / `sc_safety.c`（规则表逐条对齐） |

## 二、为什么可以拆掉（之前认为不能）

`架构-实时语音v3.md` 里列过"三条墙"。这次逐条去源码树核实，
**结论是其中两条根本不成立**：

| 原判断 | 核实结果 |
|---|---|
| 证书链不被信任，板子做不了 TLS | ❌ **判断过重**。树内 mbedtls **3.4.0**，`X509_CRT_PARSE_C` / `PEM_PARSE_C` / `ENTROPY_C` / `SSL_PROTO_TLS1_2` 全部已开；只需打开 `CONFIG_CRYPTO_MBEDTLS` |
| 系统时间 1970，证书有效期过不去 | ⚠️ 属实，但 **`rcS` 里本来就有 `ntpcstart &`**，等它同步即可 |
| 每 20ms 一帧的 base64+JSON 解析太重 | ❌ **完全站不住**。50 帧/秒 × ~1KB JSON 在 1.2GHz 的 A7 上只占个位数百分点 CPU；而且 `libwebsockets`/`cwebsocket` 源码树里就有 |
| （隐含）板子是弱单片机 | ❌ **搞错了**。`CONFIG_RAM_SIZE=961943040` ≈ **917MB DDR** |

**唯一真正绕不过的**：API Key 放在设备上就不再是秘密
（实证：把编好的固件 `strings` 一下就能抓到 WiFi 明文密码）。
但"在设备上"不等于"在固件里" —— 放 `/data` 可写分区就解决了。

## 三、线上实测事实（都验过，不是推的）

### 3.1 TLS

```
根证书指纹 SHA-256 = CB:3C:CB:B7:60:31:E5:E0:13:8F:8D:D3:9A:23:F9:DE:
                     47:FF:C3:5E:43:C1:14:4C:EA:27:D4:6A:5A:B1:CB:5F
握手结果           = TLSv1.2 / TLS-ECDHE-RSA-WITH-AES-128-GCM-SHA256
```

指纹是**把实际装进 mbedtls 的那张证书重新算出来打的**，不是复制的字符串。
这一点很重要 —— "能连上"证明不了装对了证书：
如果误装别的根证书，握手会在校验阶段失败（看起来像服务端有问题）；
而如果校验被不小心关掉，就悄无声息地失去保护，什么现象都没有。

证书链是 3 张（leaf → RapidSSL TLS RSA CA G1 → DigiCert Global Root G2），
服务端会送中间证书，所以只内嵌根证书就能拼出路径。

### 3.2 WebSocket

`Sec-WebSocket-Accept` 会校验（SHA1(key+GUID)）。多写 10 行，
但能在**中间有代理/拦截**时立刻发现 —— 否则表现为"连上了但收不到任何消息"。

### 3.3 会话

```
session.created  → voice 默认是 jingdiannvsheng（不是 linjiajiejie！）
session.update   → 下发音色 + VAD 参数
response.audio.delta → 实测一次给 10924 个 base64 字符 ≈ 4096 个 24k 样本
```

端到端复验：让它念"你好呀，我是小满，我们一起玩好不好？"（17 字）
→ 收到 **71680 个 16k 样本 ≈ 4.48 秒** → **3.8 字/秒**，正常语速。

## 四、过程中真实踩到的坑（按"花了多久才找到"排序）

### 4.1 `model` 必须走 URL query（花了最久）

```
✅ /v1/realtime?model=stepaudio-3-realtime-preview
❌ /v1/realtime                              → HTTP/1.1 400 Bad Request
```

400 是最没有信息量的错误码之一：既可能是请求格式错、也可能是缺参数。
我确实先去查了 WebSocket 握手代码。

**这条在网关的 `stepfun.py` 注释表里早就记过，写板端时还是漏了。**
说明"同一份协议知识存在两处"时，一定会漏一处。

### 4.2 `session.created` 之后必须**立刻**下发配置

否则服务端主动关闭连接。现象是"刚连上就断"，
看起来像网络问题或鉴权问题，完全不会想到是"配置发晚了"。

### 4.3 下行 base64 缓冲不能照上行尺寸推

服务端一次给 **10924 个 base64 字符** ≈ 8193 字节 ≈ **4096 个 24k 样本**。
第一版按上行尺寸（2112 样本）分配，每次解码都返回 -1，
日志刷"base64 解不开" —— 而**听感上是"机器人不说话"**。

现在缓冲取 16384 样本（4 倍余量），并且在报错时把
"需要多少 / 缓冲多少"一起打出来，免得下次又要猜。

### 4.4 群延迟是小数，别用整数滞后去测

重采样往返的群延迟是 **31.68 个样本**（@16k），不是整数。
用整数滞后对齐宽带噪声，哪怕只差 0.2 个样本，高频部分就会明显失配 ——
实测整数对齐只能到 0.93，看起来像"严重失真"，
但那是**对齐精度**的问题，不是重采样的问题。

### 4.5 构建卡在官方环境检测脚本探测 github.com（6 分半）

```
curl -o /dev/null -s -w '%{time_total}' --connect-timeout 5 https://github.com
                                        ↑ 只限制建连，不限制传输
```

从国内 ECS 访问 github 常见"TCP 连上了、HTTP 响应一直不来" →
curl **无限等下去**。而这一段是 `build_openvela.sh` 第 0 步的一部分，
于是整个构建一个字都不输出地挂着。

**现象是"构建卡住不动"**。我一开始的判断也错了：看到进程在跑、
`error` 为 0，差点以为只是"编译很慢"。是发现**3 分钟内一个 `.o`
都没更新**才意识到不对。

已修：给三个探测命令加 `--max-time 8`，SSH 探测加 `timeout 10`
和 `BatchMode=yes`（后者保证它不会挂在一个没人能回答的密码提示上）。

### 4.6 上板后暴露的三个根因（叠加在一起，每个看起来都像"网络问题"）

固件烧上去之后，现象是：**WiFi 看起来连上了，但板子一直连不到服务器**（`errno 101 ENETUNREACH`）。屏幕显示"连接中"，完全看不出是 WiFi 的事。

拆开之后是三个独立的问题叠在一起：

#### 4.6.1 板子上有一份写死了别的 AP 的配置

```
/data/etc/wifi/wapi.conf
{"wlan0": {"ssid": "Rivotek-Visitor",
           "bssid": "be:c1:a6:ff:d6:5e",
           "psk": "Rxw@2511", "auth": 4, "cmode": 8, "alg": 3}}
```

`netinit_associate.c` 的逻辑是「读到就用它，读不到才用编译期配置」——
所以 `CONFIG_NETINIT_WAPI_SSID="wifi"` **从来没生效过**。驱动一直去连
`Rivotek-Visitor`，而它的 BSSID 是写死的：

```
RTL871X: set ssid [Rivotek-Visitor]
RTL871X: rtw_select_and_join_from_scanned_queue: return _FAIL(candidate == NULL)
RTL871X: No Assoc Network After Scan Done
```

**"扫到了但连不上"** —— 看起来像信号或密码问题，实际是配置文件
把网卡钉死在了另一个 AP 上。

**更麻烦的是它在打包素材里**（`lichee/board/common/data/UDISK/etc/wifi/wapi.conf`），
所以**每次刷机都会回来**。

> ⚠️ 这份文件（以及它写死的 `be:c1:a6:ff:d6:5e`）本来就在本文档
> 早期版本里被点名为"换网络必死"的根因 —— 但当时判断它
> **不在打包素材里**，所以以为不会遇到。**判断错了。**
> 教训：文档里记下的"已知坑"，必须**在源码树里核实一遍**
> 才算真的排除，不能靠"应该不在吧"。

验证：删掉它重启后，WiFi 立刻关联成功（`AP: e6:d3:7e:9c:95:a5`、
`at RUNNING`、`ESSID: wifi`）。

#### 4.6.2 静态 IP 让"网络就绪"的判断永远为真

```
CONFIG_NETINIT_IPADDR=0x0a000002   → 10.0.0.2
CONFIG_NETINIT_DRIPADDR=0x0a000001 → 10.0.0.1
```

**不管有没有关联上 AP，wlan0 永远"有 IP"。** 而 `sc_wifi.c` 的检查
原本只判断"有没有非零 IP" → 永远返回 `SC_WIFI_OK`：

- WiFi 守卫认为网络没问题 → **从不重试**
- `sc_rt` 认为网络就绪 → 直接去连服务器 → `ENETUNREACH`

这个网段还是厂商按他们自己的测试 AP 设的，换到别的网络必然不通。

现在改为**同时要求 `IFF_RUNNING`**（那个标志只在链路层真正建立后置位），
并新增 `SC_WIFI_NO_LINK` 状态。

> 这条是**我的设计缺陷**，不是厂商的坑：
> "有 IP"和"能通信"是两件事，用前者当后者的代理条件，
> 在静态配置的场景下必然失效。

#### 4.6.3 DHCP 库开着，但 netinit 没用它

`CONFIG_NETUTILS_DHCPC=y` 本来就有，缺的只是 `CONFIG_NETINIT_DHCPC=y`。
开了之后板子在任何网络下都能拿到正确的 IP 和网关 ——
**这才是可移植的做法**（换个 WiFi 不用重编固件）。

三个修复都在 `integrate_superchild.sh` §2c 里，且会随每次集成重新应用。

### 4.7 我自己的测试错了 4 次（比产品代码的 bug 还多）

这一轮产品代码只发现 3 个真实 bug，而**测试写错了 4 次**：

| 现象 | 真实原因 |
|---|---|
| 往返相关度 0.6884，「严重失真」 | 拿同一索引比对两个**错开**的正弦。线性相位 FIR 必然有群延迟 |
| 「群延迟跨频率不恒定」 | 纯正弦的互相关函数**是周期性的**，argmax 不唯一。1kHz（周期 16 样本）被拖到了搜索边界 |
| 噪声往返只有 0.9722 | 测试噪声的频谱不像语音：一阶低通滚降只有 −6dB/oct，4~7kHz 还有大量能量，而那正好是 8kHz 通带边缘的过渡带 |
| 「64 位长度解析失败」 | 服务器的 `"BIG64:"` 是 **6** 个字符，我在 Python 里写成 `msg[7:]` → `int("0000")=0` → 服务器发了个**零长度帧**。客户端忠实地报告"收到 0 字节消息"，它是对的 |

最后一条尤其值得记：**如果直接去改产品代码，就会把对的改成错的。**

## 五、板端代码的三个设计决定

### 5.1 可移植薄层，先在宿主上验证

`sc_port.h` 用 `SC_HOST_TEST` 分叉，让 `sc_b64` / `sc_resamp` / `sc_ws` /
`sc_stepfun` / `sc_emo` / `sc_safety` **同一份源码**既能编进固件，
也能在宿主 Linux 上原生编译。

价值在于**把"协议栈对不对"和"板子环境对不对"分开**：

```
先在 ECS 上用 x86 原生编译，直连真实 StepFun 跑通  ← 协议栈正确
再交叉编译上板                                    ← 只剩 NuttX 环境问题
```

不分层的做法是：一个函数里同时有 socket、TLS、HTTP 握手、帧解析。
出错时只能看到"连不上"，得靠猜是哪一层。

宿主测试链接的是**树内那份 mbedtls 3.4.0**（用树内源码编出的 x86 静态库），
所以 API 层面不会出现"宿主能过、板上编不过"。

### 5.2 半双工闸门放在**入队前**

板子的喇叭和麦克风相距几厘米，没有 AEC。全双工的话机器人会被自己的
声音触发 VAD，然后**自己打断自己**（表现是"说半句就停、停完又从头说"）。

闸门如果放在"发送前"判，采集到的音频还是先进了环形队列，
等闸门打开时会把**几秒前的旧声音**发上去 ——
模型听到的是错位的对话，表现为**"答非所问"**，比丢一点音频糟糕得多。

判据是三条**或**关系：模型正在生成 / 播放队列非空 / 队列刚清空不超过 500ms。

> ⚠️ 不能只看 `response.done`（第一版就是这么写的）：开机问候、安全改舵、
> 手动点播这三条路径都不经过"VAD → response 生命周期"，
> 于是它们在播放期间**完全不闸断** —— 问候播到一半，孩子一开口就把问候打断了。
> 加一条"播放队列非空"就把这三条全兜住了。

### 5.3 心情用 q16 定点推进

三轴的时间常数是 240s / 90s / 25s。每 10ms 推一次的话，
整数的 `(base-cur)*dt/tau` 会被整除成 **0**，衰减**永远不发生** ——
而现象是"情绪只涨不落"，很晚才会被注意到。

所以用 16 位小数的定点，并且 int64 做乘法（避免大 dt 时溢出）。

## 六、还没上板验证的（列清楚，别当成都好了）

| 项 | 状态 | 风险 |
|---|---|---|
| mbedtls 在 NuttX 上的熵源 | ⬜ | `mbedtls_ctr_drbg_seed` 依赖 `getrandom()` 或 `/dev/urandom`。已开 `CONFIG_DEV_URANDOM` + `CONFIG_CRYPTO_RANDOM_POOL`，但没实跑过。失败现象是"TLS 初始化失败" |
| 296KB 的新代码在 1.2GHz A7 上的握手耗时 | ⬜ | 宿主上是毫秒级，但宿主是 x86。板子上 RSA-2048 握手可能需要几秒。会话任务栈给了 20KB |
| `pthread` 栈是否够 | ⬜ | 几个大对象已做成 static 绕开栈，但 mbedtls 的调用栈深度没实测 |
| 屏幕是 `/dev/lcd0` | ⬜ | 沿用 v3 的假设 |
| 24 个表情的实际观感 | ⬜ | 全部数值按比例推定 |
| NTP 是否真的同步上 | ⬜ | 证书校验的前提 |
| 麦克风/喇叭与 VAD 门限 700 的匹配 | ⬜ | 门限是按 v3 的板端标定（ADC 数字增益 205）定的 |

**上板后第一件事**：看串口日志里有没有
`tls: 根证书指纹 SHA-256 = CB:3C:...` —— 有这行说明 mbedtls 起来了。

## 七、烧录后怎么用

### 7.1 下发 API Key（**必做，否则连不上**）

Key **不在固件里**（这是刻意的：固件可以随便传、重刷、送人都不泄露密钥）。
开机从 `/data/etc/superchild/stepfun.key` 读：

```sh
mkdir -p /data/etc/superchild
echo <你的key> > /data/etc/superchild/stepfun.key
```

adb 或串口 nsh 都行。`echo` 带的换行会被 `sc_key.c` 去掉
（带换行的 key 是鉴权失败，而报错**完全看不出是换行导致的**）。

`/data` 是 YAFFS 可写分区，**重启保留**，只有整片重刷或恢复出厂才会丢。

### 7.2 可选：换角色提示词

`/data/etc/superchild/persona.txt`（没有就用内置的精简版）。

### 7.3 屏幕上角标的含义

| 角标 | 含义 | 先查 |
|---|---|---|
| （无） | 已连上会话 | 正常 |
| `o 连接中` | 有网，在连 StepFun | key 是否下发、外网是否通 |
| `! WiFi 未连` | 有网卡没 IP | 密码、路由器 |
| `! 没有 wlan0` | 网卡没起来 | RTL8733BS 驱动 |
| `x 掉线` | 连过又断了 | 看串口日志 |

WiFi 状态专门占一格是因为：**「没联网」和「它不理我」在孩子眼里表象完全一样**
（都是说了没反应），但排查方向差很远。

```sh
# 全部（在 ECS 上）
cd /root/dev_superchild
gcc -O2 -std=c11 -DSC_HOST_TEST -D_POSIX_C_SOURCE=200809L -I. \
    -o test_core test_core.c sc_port.c sc_b64.c sc_resamp.c -lm
./test_core

# WebSocket（对着本机服务器）
python3 ws_server.py 8765 &
gcc ... -o test_ws test_ws.c sc_port.c sc_b64.c sc_ws.c sc_tcp.c && ./test_ws

    sc_port.c sc_b64.c sc_resamp.c sc_ws.c sc_tls.c sc_stepfun.c \
    cjson/cJSON.c <树内 mbedtls 的 x86 静态库> -lm
./test_stepfun <API_KEY>
```
