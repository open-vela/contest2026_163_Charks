## 二、为什么要在中间放一个网关

> **先澄清一个容易误解的点**：板子**本来就必须联网** —— 它要连
> `api.stepfun.com`。所以"必须联网"不是网关引入的约束，
> 网关只是换了个地方干活。真正减少依赖的做法是**把网关放在家里**
> （见 §2.2），而不是取消网关。

### 2.1 四个理由，按"有多难啃"排序

StepFun Realtime 的接入要求是 **WSS + JSON + Base64**。
能不能全压到板子上？**技术上不是不能，但代价如下** ——
2026-09-20 我把源码树翻了一遍，结论分成四档：

| # | 理由 | 实测证据 | 难度 |
|---|---|---|---|
| 1 | **API Key 会公开** | 写进 firmware 的东西等于公开：本次构建的镜像 `strings` 一下就能抓到 WiFi 明文密码 `<WIFI_PASSWORD_REDACTED>` | ⛔ **无解**（除非你本来就不在意这把 key） |
| 2 | **TLS 能跑，但关键一层没开** | 树里有 `apps/crypto/mbedtls`，但 `CONFIG_MBEDTLS_NET_C is not set` —— **TLS 的 socket 回调层**，没有它没法在 socket 上做 TLS | 🟡 一天左右工作量 |
| 3 | **系统时间是 1970，证书有效期校验过不去** | defconfig 里**没有 RTC**（`CONFIG_RTC` 未开）；NTP 客户端在（`CONFIG_NETUTILS_NTPCLIENT_STACKSIZE` 有值）但要接线并在 TLS 之前完成同步 | 🟡 半天，且时序敏感 |
| 4 | **重采样放在哪** | StepFun 24kHz / 板上可用 16kHz | 🟢 板上也能写定点 FIR，只是 numpy 里是几十行 |
| — | ~~每 20ms 一帧的解析开销~~ | ~~base64 + JSON 逐帧解析~~ | ❌ **这条我原先夸大了**，见下 |

**关于第 5 条（原"解析开销"），收回：**

我原先写"640 字节 → base64 856 字节 + JSON，在 1.2GHz 的 A7 上逐帧解析"
是一堵墙。**这个判断站不住**：50 帧/秒 × 约 1KB 的 JSON，
在 1.2GHz 的 A7 上大概只占个位数百分点的 CPU，而且 `libwebsockets`
和 `cwebsocket` **源码树里本来就有**（`apps/netutils/`）。
这不是墙，只是"没接"。

**而且内存也不是约束**：`CONFIG_RAM_SIZE=961943040`（约 917MB DDR）。
原以为板子是个小单片机，实际不是 —— 所以**"板子太弱跑不动"这个说法也不成立**。

### 2.2 那真正不可绕的是哪一条？

**只剩第 1 条：API Key。**

这一条的性质和前三条完全不同：前三条是"要花时间接"，第 1 条是
**"只要 key 在设备上，它就不再是秘密"**。刚才 `strings` 抓到 WiFi 密码
就是实证。而 StepFun 的 key 是**计费的** —— 泄露的后果是别人花你的钱。

理论上可以给每台设备发一个受限 token + 在服务端做兑换，
但那个"服务端"**就是网关**。所以这条路绕一圈还是回到网关。

### 2.3 代价（必须写清楚）

**板子到网关这一段没有加密。** 这是刻意接受的交换 ——
可以在网关上做 IP 白名单/令牌，但如果要公网部署到产品级，
这一段应该换成 DTLS 或走内网。

**如果在意"音频经过我的 ECS"这件事**，有个很现实的折中：
把网关放到**你自己家里**（树莓派 / 旧笔记本 / 迷你主机），
板子走局域网连它。这样：

- 音频不出内网，只有"家里出口 → StepFun"这一段公网
- 不依赖我的 ECS、不依赖公网回连，延迟更低更稳
- 代码完全不用改，`config.ini` 里换个地址就行

这条路径没有做，但**架构上是支持的** —— 网关本来就是独立的 systemd 服务。

## 三、StepFun Realtime 的三个实测事实

官方文档对这三件事要么没写、要么写反了，都是探针测出来的
（`server/tools/probe_*.py` 六个探针全部留档）。

### 3.1 采样率 = 24000 Hz（文档没写）

文档只写 `pcm16`。官方《实时对话开发指南》里只在浏览器播放示例的
代码注释里出现过一次 "24000"。

**为什么不能直接信**：如果实际是 16k 而按 24k 理解，孩子听到的
声音会慢 1.5 倍、低 1.5 倍音 —— 这类问题在联调时最容易被误判成
"模型音色不好"。

三种方法交叉验证，前两种**无效**，记下来免得以后重复走：

| 方法 | 结论 | 为什么无效 / 有效 |
|---|---|---|
| 频谱悬崖法 | ❌ 无效 | 分析的频带和信号的频带是同一批样本，内容永远"填满"你假定的带宽 |
| ASR 回灌法 | ❌ 无效 | 这个模型对 1.5 倍变速相当鲁棒，两种假设都能正确转写 |
| **同音色 TTS 标定法** | ✅ 有效 | TTS 接口接受显式 `sample_rate`，用同一把嗓子当尺子 |

标定过程：TTS 以**显式 16000 Hz** 合成同一句话，测得基频 F0 = 271 Hz
（高音女声）；Realtime 同音色输出按 16k 分析得 213 Hz（偏低太多）、
按 24k 分析得 320 Hz（吻合）→ **24 kHz**。

端到端复验：回复"小星星，一闪一闪亮晶晶，真好看呀。"（17 字）
下行 4.88 秒 → 3.5 字/秒，正常语速。**采样率确认无误。**

### 3.2 首段音频延迟 0.42 秒

杭州 ECS 到 StepFun：握手 0.11s，首段音频 0.42s，完整 3.12s 语音
在 1.75s 内生成完（**约 1.8 倍实时**）。

"1.8 倍实时"这件事直接决定了网关的音频泵设计：必须**匀速往外发**，
不能"收到就发"，否则板子缓冲越积越多，表现为**越聊延迟越大**。

### 3.3 音色与模型

| 模型 | 结果 |
|---|---|
| `stepaudio-3-realtime-preview` | ✅ 可用，`linjiajiejie` 有效，首段 0.42s |
| `stepaudio-2.5-realtime` | ✅ 可用，同样接受 `linjiajiejie` |
| `step-audio-2` / `-mini` | ⚠️ 能连，但报 `voice linjiajiejie is not valid`（它们只认 `qingchunshaonv` / `wenrounansheng`），且首段延迟 7.8s |

选 `stepaudio-3-realtime-preview`：延迟最低、支持情感型音色、支持打断。

### 3.4 VAD 的行为（文档没说的坑）

- **服务端 VAD 有能量门限**，默认 2500（范围 0-5000）。板子数字 MIC
  标定后 RMS 约 -20dBFS，2500 会让**孩子小声说话直接漏检**。
  实测降到 700 才稳定。
- **`silence_duration_ms` 默认 500 太短**：孩子句中的逗号停顿会被
  判定成"说完了"。实测出现过「小星星，一闪一闪亮晶晶」被切成
  「小星星。」→ 调到 800。
- **VAD 依赖实时节奏**：探针里用 4ms/块的节奏灌数据时，
  `speech_stopped` 永远不来。真实上行必须按 20ms 一块发。

## 四、板端三个关键决定

### 4.1 表情系统从 4 维扩到 10 维

上一版（`board/child_face`）只有 4 个可调维度（眼高 / 嘴宽 / 嘴高 / 腮红），
结果 12 个表情里有一半彼此看不出差别 —— 这正是"表情看不出在变"的根因。

这一版的可调维度：

| 维度 | 说明 |
|---|---|
| 眼高 | **左右独立** —— 单眼眨（WINKING）靠它 |
| 眼宽 / 眼高低 | |
| 眼形状 | 椭圆 / 瞪大 / 闭 / 眯眼弧 / **心眼** / **星星眼** / **螺旋眼** |
| **眉毛角度** | 左右独立。表达力提升最大的一维 |
| 嘴宽 / 嘴高 / 嘴上下 | |
| **嘴角方向** | >0 上扬 = 笑，<0 下垂 = 撇嘴 |
| 腮红浓度 | |
| **头倾斜 / 弹跳** | 歪头（好奇）、上下弹（兴奋） |
| **装饰** | Zzz / 音符 / 泪 / 汗 / 星光 / 心 / 撒花 / 饼干 |
| **动作** | 抖 / 弹 / 飘 / 嚼 / 挥 / 歪头 |
| 背景色温 | 随心情在暖奶油↔冷灰紫之间插值 |

表情从 12 个扩到 **24 个**（编号是协议契约，只能往后加）：

```
 0-5   会话状态    IDLE LISTENING THINKING SPEAKING HAPPY SLEEPY
 6-11  语义回应    CURIOUS SURPRISED CONFUSED SHY PROUD SAD
12-23 新增        EXCITED LAUGHING WINKING SLEEPING LOVE SINGING
                  SCARED WAVING EATING BORED DIZZY CELEBRATE
```

### 4.2 表情 = 瞬时表情 > 会话状态 > 心情

只做"事件表情"的机器人**看起来是死的**（不说话时就僵住）；
只做"状态表情"的机器人**分不清"它懂我"和"它在放录音"**。

所以三层叠加，优先级从高到低：

```
① 瞬时表情（event）   "它懂我说什么了"   停留 0.8~1.3 秒
② 会话状态（state）   聆听 / 思考 / 说话
③ 心情（mood）        不说话时的常态脸 + 眨眼频率 + 腮红浓度
```

**瞬时表情必须短。** 留久了会推迟"说话"阶段，破坏对话节奏。

心情是三轴连续量（愉悦 / 唤醒 / 能量），随时间指数衰减回基线，
时间常数分别 240s / 90s / 25s：

```
孩子开心 → 机器人也开心（情绪传染，权重 1.0）
机器人自己说的话 → 权重 0.6（只反映"它表达出来的情绪"）
```

**闲置会睡着**：45 秒没人理 → 困倦，120 秒 → 睡着。
这是陪伴机器人最讨喜的一档，也是孩子最容易理解的一档。

心情映射到脸这件事在两端**都有实现**（网关上 `emotion.py`、
板子上 `sc_mood.c`），必须保持同一套规则 —— 不一致时会出现
"网关认为该笑、板子显示困"的拉扯，表现为表情在两帧之间反复横跳。

### 4.3 口型同步用**真实播放电平**驱动

嘴形如果只按固定节奏开合，一耳朵就能听出"假"。
板子的播放任务每写完一块音频就顺手算一个峰值电平投给界面，
嘴的张开度跟着它走。成本几乎为零，可信度提升很大。

采集侧同理：孩子说话时把麦克风电平投给界面，
眼睛会有反应 —— 这是"它在听我"最直接的证据。

### 4.4 WiFi 自动联网：链路是断的，得自己接（2026-09-20 补）

**这是"开机即对话"里最后一环，也是最容易漏的一环。**

板子的开机脚本 `rcS.nsh` 里**看起来**有自动联网：

```sh
if [ -f /data/etc/wifi/wapi.conf ]
then
  sh /etc/wifi/start_wifi.sh &
fi
```

但逐文件核对源码树之后发现**两处都断**：

| # | 断点 | 证据 |
|---|---|---|
| 1 | **那个文件根本不存在** | 打包素材 `src/etctmp/etc/wifi/` 里只有 `start_wifi.sh`，**没有** `wapi.conf` → `-f` 判断为假 → 脚本一次都不执行 |
| 2 | 就算补上文件，脚本也跑不动 | 它用 `SSID=$(grep -oP ...)` 取值，而**板上没有 grep**，nsh 也不支持 `$(...)` → SSID/PSK 全空，走到 `wapi reconnect` 时是在重连一个没配过的网卡 |

**真正可用的是官方 netinit 的编译期配置**（`apps/netutils/netinit/netinit_associate.c`）：

```c
load = wapi_load_config(ifname, NULL, &conf);
if (!load) {                       // 读不到 wapi.conf 才走这里
    conf.ssid       = CONFIG_NETINIT_WAPI_SSID;
    conf.passphrase = CONFIG_NETINIT_WAPI_PASSPHRASE;
    conf.bssid      = NULL;        // ← 不带 BSSID
}
if (conf.ssidlen > 0) wpa_driver_wext_associate(&conf);
```

**`bssid = NULL` 这一点必须注意。** `wapi.conf` 的 JSON 里 `bssid` 是
**必填字段**（`wapi_load_config` 里缺它就 `goto errout`），而 `lichee` 里
现成的样例把它写死成 `be:c1:a6:ff:d6:5e` —— 这正是项目文档里记过的
「换网络必死」的根因。**所以不要用 wapi.conf，用编译期配置。**

于是我们做三件事：

1. **编译期填 SSID/密码**：集成脚本把 `WIFI_SSID` / `WIFI_PASS`
   环境变量同步到 `CONFIG_NETINIT_WAPI_SSID` / `PASSPHRASE`
   （**用环境变量传，不写进 defconfig 提交**）。
2. **应用侧加 Wi-Fi 守卫**（`sc_wifi.c`）：netinit 只在开机那一刻关联
   一次，如果板子和路由器同时上电（很常见），那一次会赶在路由器就绪前，
   而它**不会重试**。守卫任务按 3/5/7…秒递增重试最多 12 次。
3. **状态上屏**：角标显示 `! WiFi 未连` / `! 没有 wlan0` / `o 连接中` / `x 掉线`。

> **为什么非要摆到屏幕上**：「没联网」和「它不理我」在孩子眼里表象完全
> 一样（都是说了没反应），但排查方向差得很远。不摆出来就只能靠猜 ——
> 而现场调试时最贵的恰恰是"往哪个方向猜"。

`sc_wifi.c` 用 `ioctl(SIOCGIFADDR)` 而不是 `wapi_get_ip()`：后者所在目录
是编成可执行程序 `wapi` 的（`PROGNAME = wapi`），不是库，别的应用链接不到。

**第四个坑（差点漏掉，2026-09-20 晚）：板级 defconfig 把加密方式写成了 TKIP。**

```
CONFIG_NETINIT_WAPI_CIPHERMODE_TKIP=y     → 0x00000004 (TKIP)
CONFIG_NETINIT_WAPI_ALG_TKIP=y            → 2          (TKIP)
CONFIG_NETINIT_WAPI_AUTHWPA_WPA_WPA2=y    → 0x00000006
```

而 netinit 的 **Kconfig 默认本来就是 CCMP**，厂商自己那份能用的
`wapi.conf` 样例也是 `"auth":4,"cmode":8,"alg":3`（WPA2 + AES-CCMP）。

现代路由器绝大多数是 **WPA2-AES 专用**，只支持 TKIP 的客户端会关联失败。
而且这个失败**报错极具误导性** —— `No Assoc Network After Scan Done`，
字面像是在说"扫到了但没连上"，看起来像信号问题或路由器问题，
根本不会往"加密套件不匹配"上想。

所以集成脚本现在把那三行**删掉**，让 Kconfig 用自己的默认值：

```bash
del_kv CONFIG_NETINIT_WAPI_CIPHERMODE_TKIP
del_kv CONFIG_NETINIT_WAPI_ALG_TKIP
del_kv CONFIG_NETINIT_WAPI_AUTHWPA_WPA_WPA2
```

编译后的核对面：

```
CONFIG_NETINIT_WAPI_AUTHWPA=0x00000004    (WPA2)
CONFIG_NETINIT_WAPI_CIPHERMODE=0x00000008 (CCMP)
CONFIG_NETINIT_WAPI_ALG=3                 (CCMP)
```

> 这条的教训值得记：**厂商 defconfig 里的取值不是"能用的值"，只是"他们当时用的值"。**
> 凡是与 Kconfig 默认值不一致的地方，都该问一句"为什么不一样"。

### 5.1 半双工闸门（默认开）

板子的喇叭和麦克风相距几厘米。全双工的话，机器人自己的声音会被
麦克风拾到、被 VAD 判成"孩子在说话"，然后**模型自己打断自己** ——
表现出来是"机器人说半句就停、停完又从头说"，完全没法用。

板载没有回声消除（AEC），所以采用工程上最稳的做法：
**播放期间闸断上行，播放结束再留 500ms 尾巴恢复。**

⚠️ **闸门不能只看 `response.done`**（第一版就是这么写的）：
开机问候、安全改舵、控制台点播这三条路径都不经过
"VAD speech_stopped → response 生命周期"，于是它们在播放期间
完全不闸断 —— 问候播到一半，孩子一开口就把问候打断了。
现在的判据是"模型正在生成 **或** 还在放尾音"。

代价：失去"插话打断"能力。对 2-3 岁的使用场景可以接受。
配置里 `audio.half_duplex = false` 可以关掉，等以后有 AEC 再用。

### 5.2 下行音频按实时节奏发

模型生成比实时快约 1.8 倍。收到就发 → 板子缓冲越积越多 → **越聊延迟越大**。
所以有一个匀速泵（32 B/ms），只在落后时才追帧。

⚠️ **缓冲上限不能太小**：最早写 1.5 秒，而 1.8 倍生成速度必然
堆积约 1.3 秒，刚好卡在阈值上 —— 结果每次回话都被腰斩，
现象是"机器人只说半句就停"。现在取 5 秒。
超限时只丢最旧的字节，**不发 FLUSH**（发了会把正在播的那句直接切掉）。

### 5.3 安全策略从"过滤输出"改成"给模型上缰绳"

实时语音链路里**没法事后过滤回复文本** —— 音频是模型直接生成的。
所以 `prototype/safety.py` 的 37 条规则换了个用法：

```
命中危险输入 → 不打断，而是插一条内部提示 + 触发一次新回复
              "（小提示，请照做：这个要问爸爸妈妈哦。）"
```

实测能把话题拉回兜底话术。同时系统提示词里保留了完整的红线
（`persona/SOUL.md`），两层一起用。

后置校验仍在跑（`response.audio_transcript.done` 的文本），
命中就记到控制台的"违规"列表里，用于事后评估提示词效果。

## 七、和上一版（v2）的关系

| v2 的做法 | v3 | 为什么 |
|---|---|---|
| PC 侧编排 + adb 逐条下发命令 | 板子独立应用 + 裸 TCP | v2 是为了绕开 nsh 四条硬约束；现在板子自己就是"客户端"，根本不用 nsh |
| ASR / LLM / TTS 三段分开 | 一个 Realtime 模型全包 | 少三段拼接、少三次网络往返、能打断、能理解语气 |
| 表情挂进 ai_agent 的 LVGL 通道 | 独立 NuttX 应用 | 挂进去的做法出过事：不挂调用，静态库不会链进来，镜像里根本没有这个界面 |
| RGB 灯兜底（屏幕不可靠） | 不再需要 | 屏幕是主反馈通道；RGB 仍在（走 CONFIG 帧），但降级为可选 |
| PC 侧 `demo_loop.py` 编排器 | 保留（还能用于对比测试） | 它验证过的链路仍然有效 |

**`board/child_face/` 与 `board/baidu_voice/` 保留但已归档**：
前者被 `board/superchild/sc_face.c` 取代，后者在 Realtime 方案下不再需要
（ASR/TTS 都在模型里了）。`mic_route` 已移植进 `board/superchild/sc_microute.c`。
