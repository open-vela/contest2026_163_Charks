### 3.1 ⚠️ 踩过的两个坑（都很隐蔽，值得记住）

#### 坑 1：开机时固件下载**偶发失败**，`wapi reconnect` 重试就能救回

```
[08:00:07] rtl8723f_hal_init acquire FW from file:/resource/etc/wifi/FW_NIC_BCUT.bin
[08:00:07] download_fw: download firmware FAIL! status=0x27      ← 开机时失败
[08:00:17] rtw_hal_init: hal__init fail
[08:00:17] -871x_drv - drv_open fail, bup=0                      ← 驱动没起来

[08:40:42] Chip Version Info: CHIP_8723F_..._D_CUT_1T1R_RomVer(3)  ← reconnect 后重试
[08:40:43] - download_firmware_8xxx HALMAC_RET_SUCCESS            ← 这次成功
[08:40:43] rtl8723f_hal_init Download Firmware from file success
```

**含义**：`wapi reconnect` 会**重新走一遍驱动初始化**，这一遍通常能成功。
所以**即使开机时 WiFi 是坏的，敲一条 `wapi reconnect wlan0` 就能救回来**。

> 📌 芯片是 **D_CUT**，而 SDK 里只有 `FW_NIC_ACUT.bin` / `FW_NIC_BCUT.bin`。
> **实测结论：BCUT 固件可以正常驱动 D_CUT 芯片**，不需要另找固件、也不需要联系厂商。

#### 坑 2 ★ **`save_config` 会把 BSSID 钉死**，换网络时必须清掉

`wapi save_config wlan0` 会把当前关联 AP 的 MAC 写进配置文件：

```json
{"wlan0":{"mode":2,"auth":4,"cmode":8,"alg":3,
          "ssid":"玩会吧，别真学会了",
          "bssid":"b2:5a:a3:62:88:f0",     ← save_config 自动写进去的
          "psk":"<WIFI_PASSWORD_REDACTED>"}}
```

**这个 BSSID 会让驱动只认那一个 AP。** 换了网络之后，驱动会：

```
set ssid [新SSID]
survey done event(11)                       ← 扫描正常，扫到一堆 AP
rtw_select_and_join_from_scanned_queue: return _FAIL(candidate == NULL)   ← ★ 找不到
try_to_join, but select scanning queue fail
indicate_wx_custom_event No Assoc Network After Scan Done
```

**这个报错极具误导性**：扫描明明扫到了目标 AP（信号 -28dBm 就在旁边），
却报"找不到候选网络"。排查方向极易跑偏到"中文编码问题""驱动 bug""固件版本不匹配"上
——**本次实测就把这三条都试了一遍，全部是错的** ✗

**解法**：换网络时先清 BSSID，恢复"自动选 AP"：

```bash
wapi ap wlan0 00:00:00:00:00:00
```

或者直接改 `/data/etc/wifi/wapi.conf`，把 `"bssid"` 留空
（`start_wifi.sh` 里是 `if [ -n "$BSSID" ]`，留空会跳过 `wapi ap` 那一行）。

> 完整操作卡见 `WiFi连接操作卡.md`。

### 3.2 云端调用（HTTPS）能力实测 —— R5 的关键前置　✅ **链路已跑通**

**结论：板子能调云端 HTTPS 接口，R5 可行。** 但有一个必须知道的折衷（见下）。

#### 实测记录

| 测试 | 命令 | 结果 |
|---|---|---|
| 纯 HTTP | `curl -o /data/t.txt http://www.baidu.com` | ✅ **2381 字节**，完全正常 |
| HTTPS（默认校验） | `curl https://www.baidu.com` | ❌ `curl: (60) Cert verify failed: BADCERT_NOT_TRUSTED` |
| HTTPS（`--cacert`） | `curl --cacert /resource/etc/ssl/curl/ca-certificates.crt ...` | ❌ 仍失败 |
| HTTPS（`CURL_CA_BUNDLE` 环境变量） | `set CURL_CA_BUNDLE ... ; curl ...` | ❌ 无效 |
| **HTTPS（`-k` 跳过校验）** | `curl -k https://www.baidu.com` | ✅ **2443 字节**，TLS 通道正常 |
| **★ 百度 AI 开放平台** | `curl -k -s -o /data/t.txt https://aip.baidubce.com/oauth/2.0/token` | ✅ **`EXIT=0x0`**，服务器返回业务 JSON |

**最有说服力的一条** —— 百度 AI 平台返回了真实的业务错误：

```json
{"error":"unsupported_grant_type",
 "error_description":"The authorization grant type is not supported"}
```

这不是网络错误，而是服务器**正常处理了请求**并告知缺参数 —— 证明
**TCP → TLS → HTTP → 服务器 → 响应** 整条链路完整可用 ✓

#### 证书校验失败的两个原因（都还没解决）

**原因 1：系统时间是 1970 年**（这是主因）

```
板子: Thu, Jan 01 08:50:09 1970
电脑: 2026-09-19 12:32:00        ← 差 56 年
```

TLS 证书校验强制依赖正确时钟（要判断"证书是否在有效期内"）。
板子**没有 RTC**，每次上电时钟从 0 开始。

**原因 2：CA bundle 虽然存在，但 curl 似乎没真正加载**

```
/resource/etc/ssl/curl/ca-certificates.crt    223687 字节  ✓ 文件在
--cacert <该文件>                              ✗ 仍然校验失败
```

（CA 文件路径结构 `ssl/curl/ca-certificates.crt` 看起来就是给 curl 用的，
但 `--cacert` 与 `CURL_CA_BUNDLE` 都无效 —— 也可能是"时间不对"导致的连带失败，**两者尚未分离验证**。）

#### 修「时间」这条路被堵死了（实测）

| 尝试 | 结果 |
|---|---|
| `date -s "2026-09-19 12:32:00"` | ❌ `nsh: date: argument invalid`（nsh 的 `date` 不支持设置） |
| `ntpcstart` | ❌ 服务器是 `0.pool.ntp.org;1.pool.ntp.org;2.pool.ntp.org`（**国外，校园网封 UDP 123**），`samples: 0` |
| `ntpcstart ntp.aliyun.com` | ❌ 该参数被忽略（`ntpcstart` 不支持指定服务器），仍 `samples: 0` |

> ⚠️ **注意**：`ntp.aliyun.com`（`203.107.6.88`）**ping 通，75ms** ——
> 说明**网络没问题，是 NTP 服务器地址写死在固件里**，需要重新编译才能改。

#### 对 R5 的影响与建议

| 方案 | 可行性 | 说明 |
|---|---|---|
| **A. 用 `curl -k` 先跑通** | ✅ **现在就能跑** | 能立刻验证火山/百度的接口逻辑，但**不校验证书**，有中间人风险 |
| **B. 重编译固件换 NTP 服务器** | ⬜ 需重新编译 | 改 `CONFIG_SYSTEM_NTPC_SERVER` 为国内地址（如 `ntp.aliyun.com`），并确保开机后能同步成功 |
| **C. B 完成后重测默认校验** | ⬜ 待 B | 时间对了之后再看 `--cacert` 是否生效；若仍失败再查 curl 的 CA 加载配置 |

> **建议**：**先用 A 把 R5 的业务逻辑跑通**（这是主要价值），
> 同时把 B 作为"产品化前必须做掉"的一项记录下来 ——
> 一个面向儿童的联网设备长期用 `-k` 是不可接受的。

#### 6.2.1 ⚠️ 本次复验的新发现：ADC 数字增益默认偏低约 20 dB

**出厂固件那次没发现这个问题**，因为当只录了环境底噪（峰值 −35.2 dBFS），
看起来"通了"就收工了。这次按 `analyze_wav.py` 的量化体检逐档标定，
才暴露出**厂商默认值的电平明显不够**。

**实测标定表**（板载数字 MIC，距离约 30cm、正常音量说话）：

| ADC 数字增益 | 峰值 | RMS | 体检判定 |
|---|---|---|---|
| **160（厂商默认）** | 540 (−35.7 dBFS) | 49.9 (−56.3 dBFS) | ❌ 太轻 |
| **205（本次选定）** | 32768 (0 dBFS) | **3078.1 (−20.5 dBFS)** | ✅ **可用** |
| 230 | 32768 (0 dBFS) | 5077.4 (−16.2 dBFS) | ❌ 削顶 0.51% |
| 255（满值） | 32768 (0 dBFS) | 6809.9 (−13.6 dBFS) | ❌ 削顶 2.39% |

**关键结论**：

1. 厂商默认的 160 比可用点**低约 20 dB** —— 直接拖低云端 ASR 的识别率。
2. 160~255 之间只有约 **36 dB** 的可调范围，**工作窗口并不宽**：
   拉满会削顶，默认又太轻。
3. **模拟增益（`MIC1/MIC2 gain volume`）出厂已是满值 31/31，没有余量。**
   唯一的调节手段就是 ADC 数字增益。
4. 因为声音大小随距离变化，**固定增益必然在"太轻"和"削音"之间摇摆** ——
   这正是路线图建议开启 `AI_AGENT_AUDIO_PREPROCESS`（AGC 自动增益）的
   **实测依据**（此前只是推测）。

**已落到代码**：`board/baidu_voice/mic_route.c` 新增 `mic_route_apply_gain()`，
语义为**只升不降**（不低于目标值就保持不动，避免把别人调高的设置压回去），
并带回读确认。`mic_route_enable()` 会自动调用它，调用方不需要记得手动设增益。
