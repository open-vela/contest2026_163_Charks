# 风险击穿手册

> 项目：openvela 儿童语音陪伴机器人（润芯微 Gemini-S1 / 全志 R528 / openvela 5.2）
> 本手册目的：在写任何板端业务代码之前，用 5 个低成本实验把"决定项目成败的未知"逐个变成已知。
> 任一实验不通过，都可能让后续工作作废——所以先做这 5 件事，再谈别的。

---

## 0. 怎么用这本手册

### 0.1 执行位置标记（全文通用）

本手册给每条命令都标了执行位置，**不要混着敲**：

| 标记 | 含义 |
|---|---|
| `【Windows】` | 在你自己的 Windows 电脑上执行（串口工具、Python 试验台、SD 卡烧录） |
| `【Ubuntu 虚拟机】` | 在 VMware 里的 Ubuntu 22.04 上执行（拉源码、编译、打包） |
| `【板子 nsh】` | 在开发板的串口终端里，看到 `nsh>` 提示符后执行 |

> 这是初学者最容易踩的坑：原路线图把三者混在一起写，导致你以为能在 Windows 上敲 `./build.sh`，或者在板子上敲 `repo sync`。

### 0.2 门禁规则

- **R1 必须第一个做**，它会告诉你板子到底跑没跑 openvela，直接决定 R2 的必要性。
- **R3 可以和 R2 并行**，它只在 Windows 上跑，不依赖板子。
- **R2 不通过时不要开始 R4、R5**，因为固件烧不进去，一切板端实验都无从谈起。
- **R5 允许失败**：R5 失败不影响主线，退回火山引擎作为基线继续推进即可。

### 0.3 记录要求

每个实验都配了《探板记录表.md》中的对应区块。**必须当场填**，不要凭记忆补。这些记录是后续所有设计决策的依据。

### 1.2 串口与调试

| 项 | 值 |
|---|---|
| 调试串口 | **UART0** |
| 引脚 | `UART0_TX:PF2` / `UART0_RX:PF4` |
| 其他可用串口 | `UART1`：PD21/PD22　`UART2`：PC0/PC1 |
| 串口参数 | **`1500000`，Flow Control `none`**（板子没有显示器，一切调试看串口） |
| ⚠️ 常见误区 | **不是 115200！** `1500000` 是这块板（及其 2.8 寸屏版本）的实测值。若按 115200 打开会全是乱码。115200 仅作为备选尝试，见 R1 失败预案 |

来源：同板型公开实战项目 `dhy-dh/openvela-smartband-gemini-s1` 的《Gemini S1 2.8 部署与用户使用手册》第 9 节，原文「Serial port：实际 COM 号；Speed：`1500000`；Flow Control：`none`」。

> 另有一条丝印注释：`PCM 调试口 —— 如需要连接 WIFI 模块，需要将这个排针进行跳线`。结合板级配置里 WiFi 驱动已启用、且固件自带 `start_wifi.sh`，判断**板载 WiFi 不需要跳线即可使用**；该注释针对的是外接 WiFi 模块的场景。此结论在 R1 时用 `ifconfig` 复核。

**板级配置目录**：`vendor/allwinnertech/boards/r528/r528s3-gemini-s1/configs/`

| 配置名 | 用途 |
|---|---|
| `nsh` | 基础 NSH 命令行配置 |
| `nsh_minidisplay` | 带屏显示（2.8 寸 SPI 屏）的 NSH 配置 |
| `bootloader` | Bootloader 配置 |

**编译**【Ubuntu 虚拟机】（在 openvela 工程根目录执行）：

```bash
# 仅在切换配置或改过 menuconfig 后才需要 distclean
./build.sh vendor/allwinnertech/boards/r528/r528s3-gemini-s1/configs/nsh -j2 distclean

# 编译
./build.sh vendor/allwinnertech/boards/r528/r528s3-gemini-s1/configs/nsh -j2
```

把 `nsh` 换成 `nsh_minidisplay` 或 `bootloader` 即可编译其他配置。

> **`-j2` 是刻意的保守值**（该构建带 LTO）。链接阶段可能长时间没有输出，**这是正常的，不要主动中断**。内存充裕时可以试 `-j4`，但先用 `-j2` 拿到一次成功。

**编译产物校验**【Ubuntu 虚拟机】：

```bash
test -s nuttx/nuttx
test -s nuttx/nuttx.elf
test -s nuttx/nuttx.map
test -s vendor/allwinnertech/lichee/board/r528s3/gemini-s1_nand/configs/nsh.fex
```

> **关键**：POSTBUILD 会自动执行板级处理并生成 `nsh.fex`。
> **不要手工把巨大的 `nuttx.bin` 复制成 `nsh.fex`** —— 那个文件在 pack 阶段会出问题。

**打包**【Ubuntu 虚拟机】（必须开一个新终端，且必须在 `lichee` 目录下执行）：

```bash
cd vendor/allwinnertech/lichee/
source envsetup.sh
lunch_nuttx r528s3-gemini-s1     # ← 非交互带参数，不是"选 2"
pack
```

**打包成功判据**（必须看到这两行）：

```text
Dragon execute image.cfg SUCCESS !
pack finish
```

**最终镜像**：

```text
vendor/allwinnertech/lichee/out/r528s3/gemini-s1_nand/rtos_nuttx_r528s3-gemini-s1_uart0_128Mnand.img
```

> 参考镜像大小 `68,690,944` 字节（≈65.5 MB）。改过源码或素材后大小会变。

**三条容易被忽略但会致命的事**：

1. **只编译不 `pack` 得不到可烧录镜像。** 字体、PNG、PCM、WiFi 配置等素材是在 `pack` 阶段写进 usrdata 分区的。
2. **`pack` 后必须确认 `nsh.fex` 时间戳更新了**，否则会出现"烧录完还是旧代码"这个经典坑。
3. **`dragon` 打包工具需要 32 位兼容库**。缺 `libc6-i386` 与 multilib 时 `dragon` 直接无法执行，而且报错不会指向缺依赖。依赖清单见《环境搭建手册.md》。

### 1.3.1 官方打包目标：Gemini-S1 与 DshanPi **不可混用**

官方 `vendor_allwinnertech`（分支 `dev-ai-contest-2026`）在 `lichee/board/r528s3/` 下同时提供四套打包目标：

| 打包目标 | 对应板子 |
|---|---|
| **`gemini-s1_nand`** | **本项目用这个** |
| `dshanpi_nand` | 百问网 DshanPixVela-Devkit |
| `evb4_nand` | 全志 evb4 参考板 |
| `velaevb1_nand` | vela evb1 |

**两套分区表的实际差异（已逐行核对，单位＝扇区×512字节）**：

| 分区 | `gemini-s1_nand` | `dshanpi_nand` |
|---|---|---|
| mbr | 256 KB | 256 KB |
| bootloader0 | 2048（1 MB） | 2048（1 MB） |
| dummy_1 | 262144（128 MB） | 262144（128 MB） |
| boot0-direct | 2048（1 MB） | 2048（1 MB） |
| uboot-direct | 8192（4 MB） | 8192（4 MB） |
| reserved_1 | 2048（1 MB） | 2048（1 MB） |
| sst | 2560（1.25 MB） | 2560（1.25 MB） |
| **bootloader**（下载 `nsh.fex`） | **32768（16 MB）** | **20480（10 MB）** |
| res | 51200（25 MB） | 51200（25 MB） |
| **usrdata** | **425472（207.75 MB）** | **155136（75.75 MB）** |

> **`bootloader` 与 `usrdata` 差了 2.7 倍。混用会导致白屏、触摸错位或启动崩溃**（故障表已明确记录该现象）。
>
> 判据很简单：**镜像名必须含 `gemini-s1`**。看到文件名含 `256Mnand` 就是 DshanPi 的产物，不要烧。

### 1.3.2 关于 NAND 容量冲突的核实结论

**核实过了，但静态文件无法给出确定答案**：

| 核查项 | 结果 |
|---|---|
| 官方 `sys_partition.fex` 的 `dummy_1` | gemini 与 dshanpi 都是 262144 扇区（128 MB）。该行注释称"该值表示 flash 总容量（如 524288 = 256MB）" |
| 但 gemini 逻辑分区总占用 | 约 250 MB（> 128 MB），**与该注释的语义对不上**，说明这条注释不能简单套用 |
| 官方 `sys_config.fex` 的 NAND 配置 | `storage_type = -1`（**auto scan，启动时自动探测**），静态文件不声明芯片容量 |

**结论：容量不阻塞动手。** 无论芯片是 128 还是 256 MB：

- 用 `gemini-s1_nand` 打包目标
- 烧镜像名含 `gemini-s1` 的固件

这两条与芯片容量无关，照做就是对的。容量本身降级为 **R1 顺手核对项**，确认方式见 R1 第 2.6 节。

### 1.5 AI Agent 框架接入点（来源：`packages_ai_agent` 源码树与官方文档）

**能否拿到源码**：能。官方 manifest `openvela.xml`（`dev-ai-contest-2026` 分支）中有：

**框架提供的能力**

- 多渠道接入：CLI / 飞书 / 微信 / WebSocket / MQTT / **Voice（ASR+TTS）** / Node / MCP
- 多 LLM 后端：Kimi / 通义千问 / DeepSeek / GLM / MiMo / Claude / OpenAI，含 LLM Router（最多 4 后端、复杂度感知路由、故障转移）
- 35+ 内置工具：`cron_add`（定时任务）、`music_play`（支持在线 URL，PCM/WAV/MP3）、`get_weather`、`get_current_time`、`read_file`/`write_file`（限 `/data/agent/`）、`run_shell`（三级安全策略）等
- Skills 系统：Markdown 格式，放 `/data/agent/skills/`，可对话创建
- 人格与配置：`/data/agent/config/` 下的 `SOUL.md`（人格设定）、`USER.md`（用户信息）、`config.json`（运行时配置，CLI 命令自动持久化）
- 安全加固：工具白名单、敏感工具限流、Shell 三级策略、日志脱敏
- 低内存优化：堆检测、内存池、流式输出，官方称适配 ~256KB RAM 设备

**语音通道架构与扩展点（来自 `docs/channels.md`）**

```
Mic → PCM → ASR → text → message_bus → agent_loop

```

- 内置后端：**火山引擎**

- **后端扩展点（本项目自研百度后端将使用）**：实现 `voice_tts_ops_t` 或 `voice_asr_ops_t` 接口（`init/synthesize/deinit` 或 `init/recognize/deinit`），在 `voice_channel_init()` 中调用 `register()`，即可通过 CLI 切换

### 1.7 WiFi 配置（U14）—— ✅ **已完成，两个坑记录于此**

> **原问题（2026-09-16 基于出厂固件提出）**：出厂固件**确实没有 `wapi` 命令**，
> 且 `rcS` 结尾残缺、WiFi 启动段从未执行。
> **但这条已经作废**：R2 烧入自编译固件后，**`wapi` 齐全**，WiFi 实测可用。
> 下面保留的坑是**实测踩到的真问题**，与固件无关。

**实测可用的完整流程**：

```bash
# 【板子 nsh】
wapi disconnect wlan0
wapi essid wlan0 "<你的SSID>" 1
wapi psk wlan0 "<你的密码>" 1 3        # 3 = WPA2-PSK
wapi ap wlan0 00:00:00:00:00:00        # ★ 换网络时必做，见坑 2
wapi reconnect wlan0                    # ★ 开机后必做，见坑 1
renew wlan0
ifconfig wlan0
```

#### 坑 1：开机时固件下载偶发失败 —— `wapi reconnect` 重试即可

```
[开机] rtl8723f_hal_init acquire FW .../FW_NIC_BCUT.bin
       download_fw: download firmware FAIL! status=0x27     ← 失败
       rtw_hal_init: hal__init fail / drv_open fail, bup=0  ← 驱动没起来

[reconnect 后]
       - download_firmware_8xxx HALMAC_RET_SUCCESS          ← 成功
       rtl8723f_hal_init Download Firmware from file success
```

**结论**：`wapi reconnect` 会重走一遍驱动初始化，**重试通常成功**。
芯片是 **D_CUT**，SDK 里只有 `FW_NIC_ACUT.bin`/`FW_NIC_BCUT.bin`
—— **实测 BCUT 固件能正常驱动 D_CUT 芯片**，不需要另找固件/联系厂商。

#### 坑 2 ★：`save_config` 会把 BSSID 钉死 —— 换网络必须先清零

`wapi save_config wlan0` 会把**当前关联 AP 的 MAC** 写进 `wapi.conf`。
之后驱动只认那一个 AP，换网络就会：

```
survey done event(11)                        ← 扫描正常
rtw_select_and_join_from_scanned_queue: return _FAIL(candidate == NULL)  ← ★
try_to_join, but select scanning queue fail
```

**这条报错极具误导性**：扫描明明扫到了目标 AP（-28dBm 就在旁边），
却报"找不到候选"。会让人误判成**中文编码问题 / 驱动 bug / 固件版本不匹配**
——本次实测把这三条都验证了一遍，**全部是错的**。

**解法**：`wapi ap wlan0 00:00:00:00:00:00`，或把 `wapi.conf` 的 `"bssid"` 留空。

> **注**：WiFi 通不通**不阻塞 R3**（识别率评估在 PC 上做）。
> 但它**是 R5 的前置**（云端 ASR/TTS 需要外网）—— **现在 R5 已解锁**。

### 2.1 接线（不插电时先做）

1. 找到板子上的调试串口针脚：丝印 **`UART0`**，其中 `UART0_TX:PF2`、`UART0_RX:PF4`，另需共地 GND。
2. USB 转串口模块与板子的**交叉连接**：
   - 模块 TX → 板子 RX（`PF4`）
   - 模块 RX → 板子 TX（`PF2`）
   - 模块 GND → 板子 GND
3. **串口线接好之后再插电源**，避免上电瞬间丢日志。
4. 电源用丝印标注的 `5V2A电源接口`。先确认板子上的 `电源开关` 位置。

> 若不确定 USB 转串口模块用的芯片（CH340 / CP2102 / FT232），先在 Windows 设备管理器里看端口号；没识别就装对应驱动。

### 2.2 打开串口【Windows】（**备用路径**，只在 ADB 不可用时才需要）

> ⚠️ **波特率是 `1500000`，不是 115200。** 这是本板（及其 2.8 寸屏版本）的实测值。

MobaXterm：`Session → Serial` → 选择端口 → 波特率 **`1500000`** → Data bits `8` → Parity `None` → Stop bits `1` → Flow control `None`。
PuTTY：`Connection type: Serial` → 同样参数。

**先打开串口会话，再上电。** 观察是否刷出启动日志。

> 若出现"前段正常、后段乱码"，说明 bootloader 与内核的波特率不一致，两个都试一遍
> （115200 与 1500000）。

### 2.3 上电并观察

1. 打开电源开关。
2. 串口应刷出启动日志（bootloader 信息 → 内核初始化 → 驱动加载）。
3. 等待直到出现提示符，预期形如 `nsh>`（openvela 的 nsh shell）。

### 4.1 为什么这件事风险高

1-3 岁幼儿的语音特征是：发音不准、叠词多、语速不稳、声音小、常伴气声和含糊音。通用中文 ASR 主要用成人语料训练，对幼儿语音的识别率会明显下降。**这不是"换个模型"能解决的，而是数据分布问题。**

### 4.4 通过标准与分档决策

**这一步的"通过"不是二元的是/否，而是**拿到一个可用结论：

| 字准率 | 结论 | 后续交互设计 |
|---|---|---|
| **≥ 70%** | 通过 | 走自由对话：孩子任意说，机器人理解为整句交给 LLM |
| **50% - 70%** | 有条件通过 | 改走**关键词 + 模板**：只从话里抽取关键意图（喝水/听歌/抱抱/名字/颜色），其余用预设模板回应，不把整句丢给 LLM |
| **< 50%** | 判定不通过 | **改产品形态为"陪伴型"**：机器人主动讲儿歌、鼓励洗手喝水、对拍打/声音做固定回应，不追求"听懂孩子在说什么"。这不是失败，是换了一条更稳的路（详见《入门路线图.md》的交互设计分支） |

无论落在哪一档，都要**另外单独统计"有噪声"场景的识别率**——它通常比安静场景低不少，直接决定你要不要在板端开启 `AI_AGENT_AUDIO_PREPROCESS`（降噪 + AGC）。

| 现象 | 处理 |
|---|---|
| 识别率极低（< 30%） | 先排除录音质量问题：确认转码成了 16kHz 单声道（用手机录的 48kHz 立体声直接传会显著变差）。排除后仍低，就是真实的幼儿 ASR 难题，按 < 50% 分档处理 |

### 5.2 再验证采集（**本实验最大的坑在这里**）

#### 5.2.1 先讲结论：不要被错误信息骗了

直接 `arecord` 会失败，报：

```
[SND_ERR][sunxi_codec_hw_params:1250] capture only support 1~3 channel
[SND_ERR][soc_pcm_hw_params:423]  codec_dai set hw params failed
```

**这条消息是骗人的。** 实测 `-c 1` / `-c 2` / `-c 3` / 默认**全都报同一个错**，
所以问题根本不在于你请求了几个声道。

翻驱动源码 `chips/r528/drivers/rtos-hal/hal/source/sound/codecs/sun8iw20-codec.c`
第 1250 行附近，真实判断是：

```c
} else {                                    /* 采集方向 */
    if (sunxi_get_adc_ch(codec) < 0) {
        snd_err("capture only support 1~3 channel\n");   /* ← 消息与原因不符 */
        return -EINVAL;
    }
```

而 `sunxi_get_adc_ch()` 是**去读 codec 的模拟寄存器**，看哪条输入通路被使能：

```c
读 SUNXI_ADC1_ANA_CTL → 查 MIC_PGA_EN / FMINL_EN / LINEINL_EN
读 SUNXI_ADC2_ANA_CTL → 同上
读 SUNXI_ADC3_ANA_CTL → 只查 MIC
...
if (adc1_flag || adc2_flag || adc3_flag) return 通道数;
else return -1;                            /* ← 所有输入通路都没开 */
```

**所以真实原因是：混音器里麦克风输入开关默认全部关闭。**

#### 5.2.2 修复（实测有效，可复现）

```bash
# 【板子 nsh / ADB】打开麦克风通路
amixer set 25 1     # MIC1 input switch          Off -> On
amixer set 28 1     # MIC2 input switch          Off -> On
amixer set 17 1     # ADC1_2 digital volume switch Off -> On

# 确认已生效（输出走 syslog，需要看 dmesg）
amixer get 25
dmesg | tail            # 板端没有 grep，直接看尾部或把 dmesg 拉回 PC 过滤

# 录制 3 秒 16kHz 单声道
arecord -r 16000 -f 16 -c 1 -d 3 /data/rec.wav
```

**完整参数**（usage 里没写全，这是从源码 `getopt("D:r:f:c:p:b:d:okhlvt")` 读出来的）：

| 选项 | 含义 | 默认值 |
|---|---|---|
| `-D` | PCM 设备名 | `default` |
| `-r` | 采样率 | 16000 |
| `-f` | 位深 | 16 |
| `-c` | 声道数 | **3** |
| `-p` / `-b` | period / buffer 大小 | — |
| `-d` | **录制时长（秒）** | — |
| `-t` | 录完立即回放 | — |

> **文件名是位置参数**：`arecord -d 3 /data/rec.wav`。
> usage 里完全没提这一点，很容易漏。

#### 5.2.3 ⚠️ 这个设置**不持久化**，必须写进项目代码

实测：`reboot` 后 `numid=25/28/17` **全部回到 `Off`**，
采集再次失败。完整复现链：

| 步骤 | 结果 |
|---|---|
| 重启后直接 `arecord` | ❌ 失败（文件未生成） |
| `amixer set 25 1` / `28 1` / `17 1` | 开关变 `On` |
| 再次 `arecord` | ✅ 成功，64044 字节 |
| 录音体检 | ✅ 可用（峰值 −32.7 dBFS，非零样本 99.7%） |

**对项目的直接影响**：

> **任何要在板子上采集音频的程序，都必须在打开采集设备之前先打开混音器通路。**
> 否则会出现"有时能用有时不能用"的间歇性故障——而这是最难排查的一类 bug。

建议做法（二选一，推荐后者）：
1. 开机脚本里跑一遍 `amixer set 25 1 && amixer set 28 1 && amixer set 17 1`
2. **在应用初始化代码里用 ALSA control API 打开**（更自包含，不依赖外部脚本）

> ✅ **本项目的代码已经实现了这一步**：`board/baidu_voice/mic_route.c`
> 已接进 `baidu_asr.c` 的初始化路径，后端注册/选中时自动打开，
> 失败只告警不致命。它有独立的 31 项测试（覆盖"控制项不存在""set 失败"
> "set 成功但值没变"三种失败模式）。详见 `board/baidu_voice/README.md` 第 5.0 节。

#### 5.2.4 验证录音（**不要只看文件大小**）

只看文件存在就宣布"麦克风通了"是最容易自欺欺人的做法——
一个 96KB 的文件可能全是静音、常量直流、或被削顶失真。

用配套工具做量化体检：

```bash
# 【Windows】把文件拉回来
adb pull /data/rec.wav tmp/

# 【Windows】体检（判断格式/静音/削顶/直流偏置/多声道死路）
py -3.13 prototype/analyze_wav.py tmp/rec.wav
```

**实测输出**（3 秒录音）：

```
===== r4_rec.wav  [可用] =====
  格式      : 16000 Hz / 16 bit / 1 声道
  时长      : 3.0 秒（48000 帧，96000 字节）
  声道 0    : 峰值 572 (-35.2 dBFS)  RMS 112.1 (-49.3 dBFS)  非零占比 99.6%
```

尺寸校验：3 秒 × 16000 Hz × 2 字节 × 1 声道 + 44 字节头 = **96,044 字节**，与实测完全吻合。

> `analyze_wav.py` 在 R3 录幼儿样本时同样适用——
> **每一段样本都先体检再用**，能避免把静音或失真的样本喂给 ASR 白白浪费额度。

| 现象 | 处理 |

| 音频工具"没有输出" | **正常现象**：HAL 工具走 `syslog` 不走 `printf`，要去 `dmesg` 里读（见 5.0.1） |
| 音频工具找不到 | `help` 查全量列表。实测已确认板上有：`aplay` `arecord` `aloop` `amixer` `soundcard` `nxcodec` `nxplayer` `nxrecorder` `test_aw_eq` `cmocka_driver_audio` |
| 板子跑音频测试后失联 | 优先怀疑板子挂死（不是自动重启）。`resetcause` 可区分"手动上电" vs "看门狗/异常复位"。**做板端实验前先接 USB-TTL 串口做保险** |

### 5.6 ⚠️ 内存实测：图2 的参数**可能是错的**

`free` 与 `/proc/meminfo` 都显示：

```
      total       used       free    maxused    maxfree  nused  nfree name
  950083504    2595184  947488320    4590824  947485472   2994     18 Umem
```

即**堆总量约 906 MB，可用约 903 MB**。

而图2 明确标注"**运行内存：128MB DDR3**"。两者差约 7 倍，**必有一个是错的**。

对照参考：

| 项 | 图2 标注 | 实测 | 是否吻合 |
|---|---|---|---|
| 运行内存 | 128MB DDR3 | **906 MB 堆** | ❌ **严重不符** |
| NAND | 256MB | `/data` 约 225MB（1618 × 128KB 可用） | ✅ 大致吻合 |

**这件事的影响很大**：

> 如果 906MB 属实，那么原计划里"内存极小、所有 AI 必须全上云、
> 端侧连唤醒词都吃力"的整个技术判断都要推翻——
> 906MB 足够跑本地 KWS，甚至能考虑小型端侧 ASR。

**待确认**：
1. 你手上板子的**实际内存颗粒型号/容量**（看图1 板子上的 DDR 丝印，或问润芯微客服）
2. 是否存在 128MB 与 1GB 两个硬件版本（"Gemini-S1" 可能是系列名）

> 在确认之前，代码与文档按"内存充足"处理，但**不要据此做大改动**。
> 采集 3 秒音频只占约 100KB，两种情况下都毫无压力。

## 8. 交叉问题速查

**Q：我应该先做哪个？**
A：**R1 已完成**（2026-09-16）。现在推荐的顺序是：

1. **R3**（半天，Windows，不依赖板子）—— 决定整个交互设计，性价比最高，**先做这个**
2. **R4**（1-2 天，板子）—— 音频通了才有后面，且 `/data` 里已有现成测试音频
3. **搭 Ubuntu 环境 + R2**（2-3 天）—— 与 1、2 可以并行（在虚拟机里跑，不占板子）
4. **R5**（最后）—— 需要固件能启用 AI Agent，通常等 R2 之后

**Q：怎么连板子？必须买 USB-TTL 转串口线吗？**
A：**不必。** 实测板子通过 USB Type-C 以 **ADB 设备**枚举，用 Android SDK 的 `adb` 直接进 shell：

```bash
# 【Windows】
adb devices -l        # 应看到 device:NuttX
adb shell "uname -a"
```

只有刷了不带 `adbd` 的固件时才需要回退到串口（1500000 波特率）。

**Q：WiFi 连不上怎么办？**
A：**先敲一条 `wapi reconnect wlan0`** —— 开机时固件下载偶发失败（`status=0x27`）是已知现象，
`reconnect` 会重走一遍驱动初始化，通常就好了（详见 1.7 节坑 1）。

如果**扫描能看到目标 AP，但报 `candidate == NULL` / `No Assoc Network After Scan Done`**，
那是 **BSSID 被 `save_config` 钉死**了（详见 1.7 节坑 2）。先清掉再重连：

```bash
wapi ap wlan0 00:00:00:00:00:00
wapi reconnect wlan0
renew wlan0
```

⚠️ 注意：`SYSU-SECURE` 这类 **802.1X 企业认证**网络 `wapi` 连不上（只支持 WPA2-PSK）。
校园网环境请用个人热点或家用路由。

**Q：卡住了怎么排查？**
A：按这个顺序：**硬件接线 → 驱动/menuconfig 配置 → 自己写的代码 → 云端 API → 网络**。绝大多数问题在前三层。

**Q：怎么把文件传到板子上？**
A：三种方式（**不用插拔 TF 卡**）：

| 方式 | 命令 |
|---|---|
| **adb push**（最快） | 【Windows】`adb push your.wav /data/` |
| scp | 【Windows】`scp your.wav root@<板子IP>:/data/`（板子有 `scp` + `sshd`） |
| 板端下载 | 【板子】`curl -o /data/x.wav http://<PC的IP>:8000/x.wav`（需先解决网络） |

**Q：每步都要先上板吗？**
A：不是。云端 API（百度、DeepSeek）一律**先在 Windows 的 PC 试验台里调通**，再去板子上用 C 复刻。否则你分不清是网络问题、API 问题还是代码问题。

**Q：原路线图哪些说法是错的？**
A：见下表。

| 原路线图写法 | 实际 |
|---|---|
| 模拟器配置 `goldfish-arm64-v8a-ap`（指快速入门场景） | 官方音乐播放器文档用的是 `goldfish-armeabi-v7a-ap` |
| "不能用 WSL/Docker" → 暗示必须双系统 | WSL/Docker 确实不支持，但 **VMware 虚拟机是被官方教程采用的方案**，不必装双系统 |
| nsh 里 `play /data/test.wav` 播放 | 官方音乐播放器是 **LVGL 图形界面 Demo**（`music_player &`），依赖屏幕，不适用于纯命令行场景。**实测本板的播放命令是 `aplay` / `nxplayer`** |
| `open("/dev/pcm0p", O_WRONLY)` | 节点是 **`/dev/audio/pcm0p`**（实测确认）；且应走 audio 框架的 caps/ioctl 配置，不是裸写 |
| 阶段二第 1 步先跑模拟器 | 模拟器验证不了 R528 板级驱动，对本项目价值低 |
| in defconfig 找 `CONFIG_R528_CODEC` / `CONFIG_I2S` | 实际是 `CONFIG_R528_AUDIO`、`CONFIG_SND_CODEC_SUN8IW20_AUDIOCODEC` |
| 担心 R528 算力不够解 MP3 | FFmpeg 已内置 mp3/aac/flac/opus/vorbis 解码，不成立 |
| 未提及幼儿 ASR 识别率 | **本项目最大盲点**，必须由 R3 前置验证 |
| 未提及 AI Agent 框架 / 百问网课程 | 两者都是极高价值的现成资源，详见《项目资料索引.md》 |
| **未提及进板子的方式** | 实测**不需要 USB-TTL**：板子以 ADB 设备枚举（`VID:PID = 18D1:4E11`），`adb shell` 即可 |
| **串口波特率 115200** | 本板是 **`1500000`**，Flow Control `none` |
| **烧录方式"未知，需问客服"** | 已确认：**全志 PhoenixSuit** + FEL/RST 进入下载模式 + 全盘擦除升级 |
| **编译用 `-j8`** | 用 **`-j2`**（LTO 构建的保守值），链接期长时间无输出属正常 |
| **打包用 `lunch_nuttx` 后"选 2"** | 用 **`lunch_nuttx r528s3-gemini-s1`**（非交互带参数），成功判据是 `Dragon execute image.cfg SUCCESS !` + `pack finish` |
| **依赖清单（简版）** | 官方清单含 `libc6-i386` 与 multilib —— **缺了 `dragon` 打包工具直接跑不起来** |
| **WiFi 配置脚本依赖 `wapi`** | 出厂固件确实没有 `wapi`、`rcS` 结尾残缺；**但烧入自编译固件后 `wapi` 齐全、WiFi 实测可用**（2026-09-19）。另有两条误导性极强的坑：开机固件下载偶发失败（`reconnect` 可救）、`save_config` 钉死 BSSID（`candidate == NULL`），见 1.7 节 |
