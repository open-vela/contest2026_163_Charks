# 环境搭建手册

> 目标：在**只有一个 Windows 电脑**的条件下，搭出能编译 openvela 的环境，并把硬件操作全部留在 Windows 侧。
> 你的机器：内存 16-32GB。本手册针对这个区间给了专门的参数与 swap 方案。
> 结论先行：**不需要装 Ubuntu 双系统。**

---

## 🚀 先看这里：最快路径（WSL + 一键脚本）

本手册下面讲的是 **VMware 虚拟机**方案 —— 那是**确定可行**的路线，但要花几小时
（下载 ISO、图形安装、配共享目录、装依赖）。

现在有了一条更快的路：**WSL2 + 一键脚本**，你只需动手 **5 分钟**。

```powershell
# ①【Windows：右键开始 → 终端(管理员)】
powershell -ExecutionPolicy Bypass -File "<仓库路径>\scripts\wsl_setup.ps1"
#   → 自动装 WSL + Ubuntu 22.04，并写好 .wslconfig 调整内存
#   → 若提示需要重启，重启后再跑一次同样的命令
```

```bash
# ②【WSL Ubuntu 内】
cd /mnt/c/Users/<你的用户名>/Desktop/openvela-superchild
bash scripts/build_openvela.sh
#   → 自动装依赖、repo init/sync、编译、打包
#   → 中途断了重跑即可续传
```

**完整说明见 `scripts/README.md`。**

### 为什么敢试 WSL（尽管官方说不支持）

官方文档明确写了不支持 WSL 和 Docker。我仍然建议先试，因为**成本不对等**：

| 路线 | 你的动手成本 | 风险 |
|---|---|---|
| **WSL + 脚本**（本条） | 约 5 分钟 + 一次重启 | 有——官方未验证，可能某步过不去 |
| VMware 虚拟机（下面第 1 章起） | 几小时 | 低——官方采用，确定可行 |

代价这么不对称，**先花 5 分钟试快的，失败了再回来走这条稳的**才是合理顺序。
下面第 1 章起的虚拟机方案**完整保留、随时可用**，不受影响。

构建脚本已针对 WSL 最常见的坑做了防护（源码不放 `/mnt/c`、内存不足自动检测），
详见 `scripts/README.md` 的「关于「openvela 不支持 WSL」」一节。

## 0. 核心思路：双轨分工

原路线图说"不能用 WSL/Docker"，很容易让人以为必须装双系统。实际上：

- **WSL 和 Docker 确实不支持**
- **但 VMware 虚拟机是被官方采用的方案**——润芯微自己发布的《openvela 开发环境的前置安装教程》讲的就是"在 VMware 中搭建 Ubuntu 22.04 LTS 开发环境"；openvela 社区讨论里也明确写"我们使用在 Windows 环境下的虚拟机形式进行 openvela 的环境搭建、部署"

所以正确的做法是**把工作拆成两条轨道**：

```
┌─────────────────────────┐        ┌─────────────────────────┐
│      Windows 侧          │        │   Ubuntu 22.04 虚拟机    │
│  （硬件操作，必须真的）    │        │  （编译，环境必须原生）    │
├─────────────────────────┤        ├─────────────────────────┤
│ · 串口终端 MobaXterm     │        │ · repo 拉源码            │
│ · 固件烧录               │        │ · ./build.sh 编译        │
│ · SD 卡写卡              │        │ · lichee pack 打包       │
│ · PC 试验台（Python）     │        │ · 改 packages/ai_agent   │
│ · 录音样本采集            │        │                          │
└─────────────────────────┘        └─────────────────────────┘
```

**为什么不把串口 USB 透传进虚拟机？**
可以透传（VMware 菜单：`虚拟机 → 可移动设备 → 选 USB-Serial → 连接`），但没必要：
1. 多一层透传就多一个故障点，出问题时你分不清是板子问题还是透传问题；
2. 烧录工具（尤其全志的工具）多为 Windows 原生软件；
3. Windows 上的串口工具更成熟好用。

**唯一需要跨轨做的事**：把虚拟机编译出来的固件拷到 Windows 烧录。用 VMware 共享文件夹即可，几秒钟的事。

## 1. 方案对比与选择

| 方案 | 可行性 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **VMware 虚拟机 + Ubuntu 22.04** | ✅ 官方采用 | 不破坏现有系统；出问题可快照回滚 | 编译慢一些；需要机器有足够内存 | **首选** |
| VirtualBox + Ubuntu 22.04 | ✅ 一般可行 | 免费 | 性能与稳定性略逊 | 备选 |
| U 盘双系统 | ✅ | 编译最快 | 折腾分区；有数据风险 | 机器内存 ≥32GB 且追求速度时考虑 |
| 云主机编译 | ⚠️ 部分可行 | 编译快 | **无法接串口**，硬件调试必须回本地；源码几个 GB 来回传 | 仅当本地实在跑不动时考虑 |
| WSL / Docker | ❌ 官方不支持 | — | — | **不要浪费时间** |

> 你的机器内存落在 16-32GB，**选 VMware**，并按第 4 节的参数配置。

## 2. 资源需求

**官方口径**（`dhy-dh/openvela-smartband-gemini-s1` 部署手册第 3 节 —— 同芯片、同板型的实战项目）

| 项 | 要求 |
|---|---|
| 处理器 | 64 位 x86 |
| 操作系统 | **64 位 Ubuntu 22.04 LTS**（x86_64） |
| **内存** | **至少 8 GiB，建议 16 GiB** |
| **磁盘** | **源码与工具链预留 40 GiB 以上**；若同时保存主体工程，建议总计 100 GiB |
| Shell | Bash；首次补齐依赖需联网 |
| 特殊限制 | **不支持 WSL 和 Docker** |

> 另有一份更严的口径（润芯微环境教程）：内存至少 16GB、建议 32GB；磁盘至少 80GB（虚拟机建议 ≥100GB）。
> **两个口径都指向同一结论：你 16-32GB 的机器是够的。**

**你的机器建议配置**

| 物理机内存 | 虚拟机内存 | 虚拟机磁盘 | swap | 并行核数 | 预期体验 |
|---|---|---|---|---|---|
| 32GB 以上 | 12-16GB | 100-150GB | 可不配 | `-j4` 起，可试 `-j8` | 顺畅 |
| 24-32GB | 10-12GB | 100-150GB | 建议 8GB | `-j4` | 可用 |
| **16-24GB** | **8-10GB** | **100-150GB** | **建议 8-10GB** | **`-j2`** | 能编译，首次全量约 30-60 分钟 |
| 16GB 以下 | 8GB | 100GB | 必配 10GB | `-j2` | 吃力，考虑云主机编译 |

**两处口径修正（相对本手册上一版）**：

1. **磁盘从 150GB 收敛到 100GB** —— 官方口径是 40GiB 起，100GB 已留足编译产物余量
2. **swap 从"必配"放宽到"建议/按需"** —— 官方这个构建推荐用 `-j2`，16GB 内存本身够用；
   swap 是"万一 OOM 时的兜底"，不是前置必需。**内存 ≥16GB 且用 `-j2` 时可以先不配**，报 OOM 了再配

> **`-j2` 是官方对这个构建的推荐值**（因为带 LTO），不是保守到过分的值。
> 链接阶段会长时间没有输出，**这是正常的，不要中断**。

## 4. 第二步：创建虚拟机【Windows】

### 4.1 推荐参数（针对 16-32GB 内存）

| 配置项 | 值 | 说明 |
|---|---|---|
| 安装类型 | 自定义（高级） | 便于精确控制 |
| 硬件兼容性 | 按你的 VMware 版本选默认 | |
| 处理器数量 | 1 个 | |
| **每处理器核心数** | **物理机核心数的一半**（如 8 核给 4） | 给多了宿主机卡，给少了编译慢 |
| **内存** | **8-12GB**（见第 2 节表格） | **必须是 4 的倍数** |
| 网络连接 | **NAT** | 默认即可，能访问互联网 |
| I/O 控制器 | 默认 LSI Logic | |
| 虚拟磁盘类型 | 默认 SCSI | |
| **磁盘容量** | **100-150GB** | 官方口径是源码+工具链 40GiB 起、含主体工程 100GiB。给 100GB 是稳妥值，150GB 更宽裕 |
| 磁盘存储方式 | **将虚拟磁盘拆分成多个文件** | 便于迁移 |
| 存储路径 | 剩余空间大的盘，**路径不含中文** | 含中文路径会引发各种奇怪问题 |

### 4.2 安装 Ubuntu

启动虚拟机，装载 ISO，按向导安装：

- 语言可选「中文（简体）」或 English
- **用户名建议全小写**，避免后续 SSH / 路径问题
- 设置强密码
- 安装约 30 分钟，需联网

### 4.3 安装 VMware Tools（必做）

装完系统后安装 **open-vm-tools**，这样才有共享文件夹、剪贴板互通、分辨率自适应：

```bash
# 【Ubuntu 虚拟机】
sudo apt update
sudo apt install -y open-vm-tools open-vm-tools-desktop
```

装完重启，然后配共享文件夹：VMware 菜单 `虚拟机 → 设置 → 选项 → 共享文件夹 → 总是启用`，加一个 Windows 上的目录（例如 `D:\vela-share`）。

在 Ubuntu 里访问：

```bash
# 【Ubuntu 虚拟机】
ls /mnt/hgfs/
```

> 这个共享文件夹是**双轨协作的桥梁**：编译好的固件拷到这里，Windows 侧直接就能烧录。

### 4.4 配置 swap（**按需**：内存不足时的兜底，不是前置必需）

> **修正说明**：本手册上一版把 swap 写成"16-32GB 内存必做"，这偏严了。
> 官方这个构建推荐 `-j2`，**16GB 内存本身够用**；swap 是"万一 OOM 时的兜底"。
> **内存 ≥16GB 且用 `-j2` 时可以先不配，报了 `cc1plus: out of memory` 再配。**
> 内存 <16GB 建议直接配上。

**先看当前状态**：

```bash
# 【Ubuntu 虚拟机】
sudo swapon --show      # 无输出 = 还没配
free -h
```

**创建 10GB swap**（官方教程给的做法）：

```bash
# 【Ubuntu 虚拟机】
sudo swapoff -a
sudo fallocate -l 10G /swapfile
# 若上面这条失败，改用： sudo dd if=/dev/zero of=/swapfile bs=1G count=10
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# 写入 fstab 使其开机自动挂载
echo '/swapfile swap swap defaults 0 0' | sudo tee -a /etc/fstab

# 验证
sudo swapon --show
free -h
```

**为什么必做**：编译 openvela 时单个 C++ 编译进程可能吃掉 1-2GB，并行 4-8 个进程很容易把 8-10GB 内存打满。有 swap 兜底，最差是变慢，不会失败。

### 4.5 安装 SSH（可选但推荐）

方便从 Windows 用 VS Code Remote-SSH 直接编辑虚拟机里的代码，比在虚拟机窗口里敲命令舒服得多：

```bash
# 【Ubuntu 虚拟机】
sudo apt update
sudo apt install -y openssh-server
sudo systemctl status ssh     # 显示 active (running) 即成功
ip addr                       # 记下虚拟机 IP，如 192.168.x.x
```

然后【Windows】用 VS Code 的 Remote-SSH 连接 `用户名@虚拟机IP`。

### 5.2 三个**不能省**的包（上一版漏了，会导致失败）

| 包 | 作用 | 漏了会怎样 |
|---|---|---|
| **`libc6-i386`** | x86_64 Ubuntu 的 32 位兼容库 | **`dragon` 打包工具无法执行**，且报错信息**不指向缺依赖** |
| **`gcc-multilib` / `g++-multilib`** | 32 位编译支持 | 同上 |
| **`genromfs`** | 生成 romfs 镜像 | `pack` 阶段失败 |

> **`dragon` 是全志的固件打包工具**（位于 `lichee/tools/tool/dragon`）。
> 它是 **32 位程序**，所以必须装 32 位兼容库。
> 这个坑很隐蔽 —— 报错看起来像 pack 配置问题，实际是缺系统库。

**各包用途速览**：

| 类别 | 包 |
|---|---|
| 版本控制与下载 | `git`、`git-lfs`、`curl` |
| 构建系统 | `cmake`、`build-essential`、`automake`、`libtool` |
| 配置系统 | `kconfig-frontends`、`bison`、`flex`、`gperf`、`gettext`、`texinfo` |
| 终端库与头文件 | `libncurses5-dev`、`libncursesw5-dev`、`xxd` |
| 交叉工具链依赖 | `libgmp-dev`、`libmpc-dev`、`libmpfr-dev`、`libisl-dev`、`binutils-dev`、`libelf-dev`、`libexpat1-dev` |
| **32 位兼容（关键）** | **`libc6-i386`**、`gcc-multilib`、`g++-multilib` |
| 文件系统工具 | **`genromfs`**、`mtools`、`unionfs-fuse`、`util-linux`、`u-boot-tools` |
| 设备与调试 | `dfu-util`、`picocom`、`libusb-1.0-0-dev` |
| 显示/视频 | `libx11-dev`、`libxext-dev`、`libv4l-dev` |
| Node（部分工具用） | `nodejs`、`npm` |
| 汇编与压缩 | `nasm`、`yasm`、`zlib1g-dev`、`libdivsufsort-dev` |
| 协议与 C++ | `libprotobuf-dev`、`protobuf-compiler`、`protobuf-c-compiler`、`libc++-dev`、`libc++abi-dev`、`libuv1-dev` |
| 网络工具 | `net-tools`、`pkgconf` |
| Python | `python3`、`python3-pip`、`python-is-python3`；另需 `kconfiglib`、`pyelftools`、`cxxfilt` |

### 5.3 安装 Git LFS（**必装，漏了会拉到坏文件**）

openvela 仓库里有大文件，不用 LFS 会拉到损坏文件，且症状很隐蔽（编译时报莫名其妙的错误）：

```bash
# 【Ubuntu 虚拟机】
sudo apt install -y git-lfs
git lfs install
# 预期输出：Git LFS initialized.
```

### 5.4 安装 repo 工具

`repo` 是 Google 的多仓库管理工具，openvela 用它拉整套源码：

```bash
# 【Ubuntu 虚拟机】
mkdir -p ~/bin

# 优先用国内镜像（Google 源在国内通常不通，且本机已实测 GitHub 的 raw 域名超时）
curl -s https://mirrors.tuna.tsinghua.edu.cn/git/git-repo -o ~/bin/repo
# 备选（若清华源也不通）：改用中科大 https://mirrors.ustc.edu.cn/git/git-repo
# 再备选（需要科学网络）：https://storage.googleapis.com/git-repo-downloads/repo

chmod a+x ~/bin/repo
export PATH=$HOME/bin:$PATH
echo 'export PATH=$HOME/bin:$PATH' >> ~/.bashrc

# 验证
repo --version
```

> ⚠️ **本机网络实测**：`raw.githubusercontent.com` 与 `codeload.github.com` **均超时不可达**，
> `api.github.com` 与 `gitee.com` 正常。所以**涉及 GitHub raw 地址的下载一律要换镜像或走 Gitee**。

## 6. 第四步：拉取源码并编译【Ubuntu 虚拟机】

### 6.1 配置 Git 身份

```bash
# 【Ubuntu 虚拟机】
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

### 6.2 配置 Gitee SSH 公钥（可选，HTTPS 也可用）

```bash
# 【Ubuntu 虚拟机】
ssh-keygen -t rsa -b 4096 -C "你的邮箱"     # 一路回车
cat ~/.ssh/id_rsa.pub                        # 复制输出
```

把公钥贴到 Gitee：`设置 → SSH 公钥 → 添加公钥`。验证：`ssh -T git@gitee.com`。

### 6.3 拉取源码（**分支必须选对**）

```bash
# 【Ubuntu 虚拟机】
mkdir -p ~/openvela && cd ~/openvela

repo init -u https://gitee.com/open-vela/manifests.git -b dev-ai-contest-2026 -m openvela.xml
repo sync -c -j8
```

| 参数 | 为什么这么写 |
|---|---|
| `-b dev-ai-contest-2026` | **必须用这个分支**。Gemini-S1 的板级支持在这个分支上；`dev` 分支**没有** `r528s3-gemini-s1` 目录 |
| `-m openvela.xml` | 主 manifest，其中已包含 `<project path="packages/ai_agent" name="packages_ai_agent"/>`，即官方 AI Agent 框架会自动到位 |
| `-c` | 只同步当前分支，显著省流量和磁盘 |
| `-j8` | 并行数，内存吃紧就降到 `-j4` |

首次同步几个 GB，**20-60 分钟**，耐心等。

> 注意：GitHub 上 `trunk-5.5` **标签**下的 `vendor_allwinnertech` 切出来无法编译。别用标签，用分支。

### 6.4 同步完成后立即验证 4 件事

```bash
# 【Ubuntu 虚拟机】
cd ~/openvela

# ① 板级目录存在
ls vendor/allwinnertech/boards/r528/r528s3-gemini-s1/

# ② AI Agent 源码存在
ls packages/ai_agent/

# ③ 分支正确
git -C vendor/allwinnertech branch --show-current      # 应为 dev-ai-contest-2026

# ④ 固件打包目标存在（★ 新增，很关键）
ls vendor/allwinnertech/lichee/board/r528s3/gemini-s1_nand/
# 预期看到：bin/  configs/  sign_config/  version/
ls vendor/allwinnertech/lichee/board/r528s3/gemini-s1_nand/configs/sys_partition.fex
ls -l vendor/allwinnertech/lichee/tools/tool/dragon
```

四条都满足才能往下走。

> **第 ④ 条的意义**：`pack` 能不能产出 Gemini 镜像，取决于这个打包目标是否存在。
> 官方 `dev-ai-contest-2026` 分支**已包含**它（同时还有 `dshanpi_nand` / `evb4_nand` / `velaevb1_nand`），
> 所以**不需要**向厂商额外索取适配包。**用错了打包目标就会产出不能用的镜像。**

### 6.5 编译

```bash
# 【Ubuntu 虚拟机】
cd ~/openvela

# -j2 是官方对这个构建（带 LTO）的推荐值
./build.sh vendor/allwinnertech/boards/r528/r528s3-gemini-s1/configs/nsh -j2
```

> - 注意路径是 `vendor/allwinnertech`，不是 `vendor/openvela`
> - **链接阶段会长时间没有输出，这是 LTO 构建的正常现象，不要中断**
> - 内存充裕（≥32GB 且虚拟机给了 16GB）可以试 `-j4`，但先用 `-j2` 拿到一次成功

**编译产物校验（必须全部通过）**：

```bash
# 【Ubuntu 虚拟机】
test -s nuttx/nuttx
test -s nuttx/nuttx.elf
test -s nuttx/nuttx.map
test -s vendor/allwinnertech/lichee/board/r528s3/gemini-s1_nand/configs/nsh.fex
```

> **POSTBUILD 会自动生成 `nsh.fex`**。
> **不要手工把巨大的 `nuttx.bin` 复制成 `nsh.fex`** —— 那样 pack 阶段会出问题。

### 6.6 打包

**必须开一个新终端**，且必须在 `lichee` 目录下执行：

```bash
# 【Ubuntu 虚拟机】
cd ~/openvela/vendor/allwinnertech/lichee/
source envsetup.sh
lunch_nuttx r528s3-gemini-s1     # ← 非交互带参数，不是"选 2"
pack
```

**成功判据（必须看到这两行）**：

```text
Dragon execute image.cfg SUCCESS !
pack finish
```

**最终镜像**：

```text
vendor/allwinnertech/lichee/out/r528s3/gemini-s1_nand/rtos_nuttx_r528s3-gemini-s1_uart0_128Mnand.img
```

参考大小 `68,690,944` 字节。

**校验并记录**：

```bash
# 【Ubuntu 虚拟机】
export IMAGE="$HOME/openvela/vendor/allwinnertech/lichee/out/r528s3/gemini-s1_nand/rtos_nuttx_r528s3-gemini-s1_uart0_128Mnand.img"
test -s "$IMAGE" && stat "$IMAGE" && sha256sum "$IMAGE"
```

**⚠️ 三条容易忽略但会致命的事**：

1. **只编译不 `pack` 得不到可烧录镜像** —— 字体、PNG、PCM、WiFi 配置等素材是在 `pack` 阶段写进 usrdata 分区的
2. **`pack` 前必须确认 `nsh.fex` 时间戳更新了** —— 否则会出现"烧录完还是旧代码"这个经典坑
3. **`dragon` 需要 32 位兼容库** —— 缺 `libc6-i386` 时它直接无法执行（见 5.2 节）

### 6.7 把固件拷到 Windows

```bash
# 【Ubuntu 虚拟机】假设共享文件夹已配好
cp <固件文件> /mnt/hgfs/<你的共享目录>/
```

然后【Windows】在共享目录里就能看到，直接拿去烧录。

## 8. 两侧协作方式

| 需求 | 做法 |
|---|---|
| 虚拟机 → Windows 传固件 | VMware 共享文件夹 `/mnt/hgfs/` |
| Windows → 板子传文件 | TF 卡拷贝 / `adb push` / 板端 `curl` 下载 |
| Windows ↔ 虚拟机 编辑代码 | VS Code Remote-SSH |
| Windows 看板子串口 | MobaXterm（不经过虚拟机） |
| 复制粘贴命令 | 装好 open-vm-tools 后可直接双向复制 |

**为什么不让串口走虚拟机**：见第 0 节。保持"虚拟机只负责编译、Windows 只负责硬件"这条界线清晰，出问题时排查范围小一半。

## 9. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `cc1plus: out of memory` | 内存不足 | 降 `-j` 到 2 或 4；确认 swap 已生效（`free -h` 看 Swap 行）；关掉宿主机上吃内存的程序 |
| 编译很慢 | 核数给少了 / swap 在换页 | 检查虚拟机核数是否为物理机一半；确认没在疯狂用 swap（`free -h` 看 swap 变化） |
| `cmake: command not found` | 依赖没装全 | 按 **5.1 节的官方完整清单**重装一遍，别只装几个 |
| `repo: command not found` | PATH 没生效 | `source ~/.bashrc` 或在新终端里重试 |
| 下载 repo 脚本超时 | **Google 源国内不通** | 改用清华镜像 `https://mirrors.tuna.tsinghua.edu.cn/git/git-repo` |
| 任何 `raw.githubusercontent.com` 的下载超时 | **实测该域名不可达** | 换 Gitee 镜像；取 GitHub 文件改用 `api.github.com` |
| `repo sync` 中途失败 | 网络抖动 | 直接重新执行 `repo sync -c -j8`，它会断点续传 |
| 拉到的文件损坏 / 编译报奇怪错误 | 没装 Git LFS | `git lfs install` 后重新 `repo sync`；必要时 `rm -rf` 对应目录重拉 |
| 找不到 `r528s3-gemini-s1` 目录 | 分支拉错 | `repo init` 必须用 `-b dev-ai-contest-2026`；检查 `repo manifest` 输出 |
| **链接阶段长时间无输出** | **LTO 构建的正常现象** | **等待即可，不要中断** |
| **`dragon` 无法执行 / pack 报莫名错误** | **缺 32 位兼容库** | 装 **`libc6-i386`** + `gcc-multilib` + `g++-multilib`（见 5.2 节）。报错不会指向缺依赖，最容易误判 |
| **`pack` 报错** | 环境或参数不对 | ① 是否在 `lichee` 目录下 `source envsetup.sh`；② `lunch_nuttx` 参数是否为 `r528s3-gemini-s1`；③ 确认 `nsh.fex` 已生成且时间戳更新 |
| **`pack` 成功但烧录后还是旧代码** | `nsh.fex` 没更新 | 先编译 → 确认 `nsh.fex` 时间戳 → 再 pack |
| 找不到 `dragon` | 打包工具路径不对 | 应在 `lichee/tools/tool/dragon`；用 6.4 节第 ④ 条的 `ls -l` 确认存在 |
| 虚拟机里中文路径报错 | 路径含中文 | 移动到纯 ASCII 路径 |
| 共享文件夹看不到 | 没装 open-vm-tools | `sudo apt install -y open-vm-tools open-vm-tools-desktop` 后重启 |
| 磁盘不够 | 给得太小 | 扩到 100GB 起；VMware 里扩展磁盘后再用 `gparted` 在 Ubuntu 内分配 |
| 编译到一半失败且看不出原因 | — | 加 `-V=s` 看详细命令；把第一处 `error` 的完整输出记下来去社区问 |

> **一类隐蔽问题的通用排查思路**：如果报错信息看起来跟你的操作没关系
> （例如 pack 报奇怪错误、工具"找不到"却明明存在），
> **优先怀疑缺系统库或 32 位兼容层**，而不是配置写错。
