### 4.1 ⚠️ 必须补的一步：WAV 格式转换（否则板子播不了）

**把 Windows TTS 产出的 wav 直接 `aplay` 到板子上会失败** —— 实测 dmesg：

```
rate:         22050
data size:    3995099508        <- 荒谬：4GB，而文件只有 257,614 字节
read file error, r=1570,c=2048  <- 读到文件尾报错，播放中断
```

**原因**：`System.Speech` 输出的是 **`WAVE_FORMAT_EXTENSIBLE`**（fmt 块带扩展字段），
**数据块不在固定偏移 44**。而 NuttX 的 wav 解析器按标准 44 字节头定位，
于是把别处的字节当成 data size 读，得到 4GB 这种离谱数字。

**修法**：过一个转换脚本，重写成规范的标准 PCM WAV：

```powershell
py -3.13 prototype/wav_for_board.py tmp/reply.wav tmp/reply_board.wav
```

它同时把采样率统一到 **16kHz**（与板端录音、ASR 输入规格一致）。

**修复前后对照（同一段音频）**：

| | 修复前 | 修复后 |
|---|---|---|
| rate | 22050 | **16000** |
| **`data size`** | **3995099508** ✗ | **186898** ✓（与文件精确吻合） |
| `read file error` | ✗ 报错中断 | ✅ 无 |
| 收尾 | 报错 | `snd_vela_pcm_close` 正常收尾 |

> **教训**：**"文件推过去了、`aplay` 没报错"不等于"播出来了"** ✗
> —— 必须去 `dmesg` 看 `data size` 是否与文件字节数吻合。这是本次唯一的"差点漏掉"的点。

## 四、实际操作步骤（换成你自己的声音）

```powershell
# ---------- 第 1 步：板端录音 ----------
# 必须先打开混音器通路，否则录到的全是静音（重启后失效，每次都要做）
adb shell "amixer set 25 1 ; amixer set 28 1 ; amixer set 17 1"
# 把 ADC 数字增益设到实测标定的工作点 205（厂商默认 160 偏低约 20dB）
adb shell "amixer set 19 205 ; amixer set 20 205"

# 录 5 秒 —— 请在执行后立刻对着板子说话
adb shell "arecord -r 16000 -f 16 -c 1 -d 5 /data/my_voice.wav"

# ---------- 第 2 步：拉回 PC 并体检 ----------
adb pull /data/my_voice.wav tmp/my_voice.wav
py -3.13 prototype/analyze_wav.py tmp/my_voice.wav
#   ↑ 看峰值/RMS/非零占比。若是"太轻"或"削顶"，先调 amixer 增益再录

# ---------- 第 3 步：本地识别（0 成本） ----------
py -3.13 prototype/transcribe_one.py tmp/my_voice.wav

# ---------- 第 4 步：合成回复 ----------
# 把回复文字写进 UTF-8 文件（不要用命令行传中文，编码会出问题）
# 然后：
powershell -ExecutionPolicy Bypass -File tools/tts_say.ps1 `
    -TextFile tmp/reply.txt -OutWav tmp/reply.wav

# ---------- 第 4.5 步：★ 转成板子能播的标准 WAV（这一步不能省！）----------
py -3.13 prototype/wav_for_board.py tmp/reply.wav tmp/reply_board.wav

# ---------- 第 5 步：推回板子播放 ----------
adb push tmp/reply_board.wav /data/reply_board.wav
adb shell "aplay /data/reply_board.wav"

# ---------- 第 6 步：★ 用 dmesg 确认真的播出来了（别只看 aplay 没报错）----------
adb shell "dmesg"
#   看 data size 是否等于「文件字节数 - 44」。不相符就是格式问题，见 4.1 节
```

## 五、两个工具的说明

### `prototype/transcribe_one.py` —— 单文件识别

```powershell
py -3.13 transcribe_one.py <file.wav>
py -3.13 transcribe_one.py <file.wav> openai/whisper-medium   # 更准但慢很多
```

- 复用 `local_asr_eval.py` 的 Whisper 加载与繁转简，**不重复实现**
- 内置**静音保护**：整段接近静音时直接报错退出，不让 Whisper 去"幻觉"出一句话
  （Whisper 在静音输入上偶尔会吐出训练语料里的句子，会把结论带偏）

### `tools/tts_say.ps1` —— 文字转语音

```powershell
powershell -ExecutionPolicy Bypass -File tools/tts_say.ps1 `
    -TextFile <输入.txt> -OutWav <输出.wav> [-Rate -2] [-Volume 100]
```

- **文字必须从文件读**，不走命令行 —— 中文在「PowerShell → 原生程序」那一跳会被重新编码
- ⚠️ **本文件必须保持「UTF-8 带 BOM」**，否则 PS 5.1 会按 GBK 解析而报语法错误。
  检查方法：`[IO.File]::ReadAllBytes("tools/tts_say.ps1")[0..2]` 应为 `239,187,191`
- 找不到 zh-CN 语音时**直接报错退出**（用英文嗓音读中文只会得到噪音，结论会失真）

## 六、踩过的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| PS 5.1 按 GBK 解析 `.ps1` | 中文变 `鎶辨姳`、脚本语法报错 | 保存为 **UTF-8 带 BOM** |
| 中文经命令行传参 | 编码被重新转换，不可靠 | 一律**从 UTF-8 文件读** |
| 板端录音是静音 | `arecord` 成功但文件全是 0 | 先开混音器通路 `amixer set 25/28/17 1` |
| 只看文件大小 | 96KB 文件可能全是静音 | 用 `analyze_wav.py` 做量化体检 |
| `aplay` 看不到输出 | 输出走 syslog 不走 stdout | 去 `dmesg` 里读 |

## 六·五、⚠️ 听不到声音：先查物理连接，不是软件问题

**2026-09-19 实测：软件侧已确认全部到位**（`amixer get` 逐项核对）：

| 控制项 | 当前值 | 说明 |
|---|---|---|
| `numid=32` Playback audio route | **`lo+hp+spk`** | lineout + 耳机 + 喇叭 **三个全开** |
| `numid=5` DAC digital volume switch | `On` | 已开 |
| `numid=6` / `numid=7` DACL/DACR digital volume | `255 / 255` | 已满（max=255） |
| `numid=16` LINEOUT volume | `31 / 31` | 已满（max=31） |
| `numid=15` HPOUT gain volume | **`7 / 7`** | **出厂默认只有 `4/7`**，已拉满 |

**结论：这块板子没有内置喇叭** ✗

板子规格里写的是「扬声器：**2 路 Speaker 接口**（左右声道）」——
**是排针，需要外接**。软件把 PCM 送到 DAC 了、`prepare` 成功了、正常收尾了，
但**没有物理喇叭把电信号变成声音**。

**两个办法**：

1. **插 3.5mm 耳机**到板子的耳机口（HPOUT）—— 最快，也是本次建议先试的
2. **接喇叭到 `SPK_L` / `SPK_R` 排针** —— 注意用**有源音箱**或确认喇叭阻抗匹配

> 本项目 R4 的通过标准里其实早就写明了这一点：
> 「要确认**实际出声**仍需你接上 `SPK_L`/`SPK_R` 或 `HPOUT` 用耳朵验一次
> （这一步机器替代不了）」。

**顺带一条经验**：`HPOUT gain volume` 出厂只有 `4/7` —— 用耳机时若觉得声音偏小，
先查这一项，别急着怀疑音频链路。
