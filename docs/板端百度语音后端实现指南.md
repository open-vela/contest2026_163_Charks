# 板端百度语音后端实现指南

> 目标：在 openvela 官方 AI Agent 框架（`packages/ai_agent`）里新增一个**百度**语音后端，
> 替代内置的火山引擎，以换取百度 5 万次/月的免费额度。
>
> 对应《风险击穿手册.md》的 **R5 实验**。
>
> 阅读前提：已完成 R2（能编译能烧录）、能启用 AI Agent、已跑通火山基线。

---

## 0. 先看清一件事：这项工作比想象中简单

读完官方源码后有两条关键判断：

**判断一：官方明确支持后端扩展，这是设计内的用法，不是逆向工程。**

`docs/channels.md` 原文：

> 实现 `voice_tts_ops_t` 或 `voice_asr_ops_t` 接口（`init/synthesize/deinit` 或 `init/recognize/deinit`），
> 在 `voice_channel_init()` 中调用 `register()`，即可通过 CLI 切换。

**判断二：百度比火山好实现。**

火山走的是 **WebSocket + 火山私有二进制帧协议**（TLS 连接 → HTTP Upgrade → 自定义帧封装），
复杂度很高。而百度短语音识别 / 语音合成都是**普通 HTTPS POST + JSON**，
用板端已有的 `curl` 库能力（或 mbedtls + socket）就能做，**不需要 WebSocket**。

所以整体工作量是：照抄 `volc_asr.c` / `volc_tts.c` 的**文件组织与凭据处理**，
把中间的传输逻辑换成简单的 HTTPS 调用。

## 3. 两个关键设计决策

### 3.1 百度 ASR：用 `format: "pcm"`，不要用 `"wav"`

百度短语音识别的 `format` 参数支持 `pcm` / `wav` / `amr` / `m4a`。

因为接口给的就是裸 PCM，**直接声明 `format: "pcm"` 即可，不需要自己拼 44 字节 WAV 头**。

```json
{
  "format": "pcm",
  "rate": 16000,
  "channel": 1,
  "cuid": "openvela-superchild",
  "token": "<access_token>",
  "len": <pcm_len>,
  "speech": "<base64(pcm_data)>",
  "dev_pid": 1537
}
```

- `len` 是**原始 PCM 字节数**，不是 base64 之后的长度。这里最容易写错。
- `dev_pid`：1537 = 普通话（带标点），1536 = 普通话（不带标点）。

### 3.2 百度 TTS：优先 `aue=4` 拿 PCM；否则用 `aue=6` 并把 WAV 头剥掉

接口要求返回裸 PCM，而百度 TTS 的 `aue` 参数决定返回格式：

| `aue` | 返回 | 能不能直接用 |
|---|---|---|
| 3（默认） | mp3 | ❌ 要解码，板端虽然能解但没必要 |
| **4** | **pcm**（16k） | ✅ **首选**，直接就是接口要的格式 |
| 5 | pcm（8k） | ❌ 采样率不对 |
| 6 | wav | ⚠️ 需要**跳过前 44 字节** WAV 头再返回 |

**实现策略**：

1. 先按 `aue=4` 实现并实测；
2. 如果百度返回的仍是带头的 wav（或 `aue=4` 对该账号不可用），就加一个**健壮的头检测**：

```c
/* 不要无脑跳过 44 字节：先确认确实是 RIFF/WAVE 头再跳过，否则会吃掉真实音频 */
static size_t skip_wav_header(const unsigned char *buf, size_t len)
{
    if (len > 12 &&
        memcmp(buf, "RIFF", 4) == 0 &&
        memcmp(buf + 8, "WAVE", 4) == 0)
    {
        /* 从头往后找 "data" 子块，比硬编码 44 更稳 */
        for (size_t off = 12; off + 8 <= len; )
        {
            const unsigned char *id = buf + off;
            uint32_t sz = (uint32_t)id[4] |
                          ((uint32_t)id[5] << 8) |
                          ((uint32_t)id[6] << 16) |
                          ((uint32_t)id[7] << 24);
            if (memcmp(id, "data", 4) == 0)
            {
                return off + 8;           /* PCM 数据起点 */
            }
            off += 8 + sz + (sz & 1);     /* 块对齐 */
        }
        return 44;                        /* 兜底：按标准头长度 */
    }
    return 0;  /* 本来就是裸 PCM */
}
```

> 这段逻辑建议**同时写进 PC 试验台的对照说明**：PC 上的 `tts.py` 用的是 `aue=6`（wav，
> 方便落盘试听），板端用 `aue=4`（PCM，接口直用）。两处 `aue` 不同是**故意的**，不是不一致。

### 3.3 「假流式」：不写 WebSocket 也能满足流式接口

如果 2.1 的结论是主流程走流式接口，**不要**去实现百度的实时语音 WebSocket 协议。用这个办法：

**ASR 假流式**：

```c
struct voice_asr_stream {
    unsigned char *buf;      /* 累积所有分片 */
    size_t         len;
    size_t         cap;
};

voice_asr_stream_t *baidu_asr_stream_open(void)
{
    /* 开一个动态缓冲，上限按录音时长上限算（3 秒 16k/16bit/mono ≈ 96KB，
       留 3 倍余量 → 300KB 上限，超了就拒绝新增） */
    ...
}

int baidu_asr_stream_send(voice_asr_stream_t *s, const unsigned char *pcm, size_t len)
{
    /* 只做追加，不发网络请求 */
    ...
}

int baidu_asr_stream_finish(voice_asr_stream_t *s, char *text_out, size_t text_cap)
{
    /* 在这里做**一次**非流式请求：复用 baidu_asr_recognize() 的逻辑 */
    int rc = baidu_recognize_internal(s->buf, s->len, text_out, text_cap);
    free(s->buf);
    free(s);
    return rc;
}
```

**TTS 假流式**：

```c
int baidu_tts_speak_stream(const char *text,
                           voice_tts_chunk_cb cb, void *user_data)
{
    /* 一次性合成，然后整块回调一次，is_last=1 */
    unsigned char *pcm = malloc(TTS_MAX_PCM);
    size_t len = 0;
    int rc = baidu_tts_synthesize_internal(text, pcm, TTS_MAX_PCM, &len);
    if (rc == 0) {
        cb(pcm, len, 1, user_data);
    }
    free(pcm);
    return rc;
}
```

**代价**：失去了流式的低延迟优势（要等说完才能开始识别）。
**收益**：实现量从"写一个 WebSocket 客户端 + 百度实时协议"降到"加一个数组缓冲"，
对一个每天只跑几十次的原型来说这个取舍完全值得。

> 如果以后真要压延迟，再单独做流式版本，不要在第一版就上。

## 5. `baidu_asr.c` 实现要点

### 5.1 文件骨架（示意，请以 `volc_asr.c` 的真实写法为准）

```c
/*
 * Baidu short-speech ASR backend for the openvela AI Agent voice framework.
 *
 * Endpoint: POST https://vop.baidu.com/server_api  (JSON + base64 PCM)
 * Auth:     POST https://aip.baidubce.com/oauth/2.0/token (OAuth2, 有效期 30 天)
 */

#include "voice/baidu_asr.h"
#include "infra/config_store.h"
#include "voice/voice_asr.h"

#include "cJSON.h"
#include "mbedtls/base64.h"        /* 或 netutils/base64.h，按 volc_asr.c 的用法选 */
#include "mbedtls/ssl.h"
#include "mbedtls/net_sockets.h"
#include "mbedtls/ctr_drbg.h"

#include <errno.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

static const char *TAG = "baidu_asr";

#define BAIDU_TOKEN_URL "https://aip.baidubce.com/oauth/2.0/token"
#define BAIDU_ASR_URL   "https://vop.baidu.com/server_api"

/* 凭据 */
static char g_api_key[128];
static char g_secret_key[128];
static char g_access_token[256];
static time_t g_token_expire_at;

/* ── init：从 config store 读凭据，并尝试换 token ───────────────── */
static int baidu_asr_init(void)
{
    int rc = config_store_get_str("baidu_api_key", g_api_key, sizeof(g_api_key));
    if (rc < 0) {
        AGENT_LOGE(TAG, "缺少 baidu_api_key，请先执行 set_baidu_key");
        return rc;
    }
    /* 同理读 baidu_secret_key */
    /* 尝试换 access_token（失败不致命——首次 recognize 时还会再试） */
    baidu_token_refresh();
    return 0;
}

/* ── recognize：核心 ─────────────────────────────────────────────── */
static int baidu_asr_recognize_impl(const unsigned char *pcm_data,
                                    size_t pcm_len,
                                    char *text_out,
                                    size_t text_cap)
{
    /* 1. 参数与前置检查 */
    if (!pcm_data || pcm_len == 0 || !text_out || text_cap == 0) return -EINVAL;
    text_out[0] = '\0';
    if (pcm_len < 3200) {          /* < 0.1 秒，多半是误触发 */
        AGENT_LOGW(TAG, "PCM 过短(%zu 字节)，跳过识别", pcm_len);
        return 0;                  /* 返回空文本，不算错误 */
    }

    /* 2. 确保 token 有效（过期前提前刷新） */
    baidu_token_ensure();

    /* 3. base64 编码 PCM —— 注意 buffer 按 4/3 放大并留余量 */
    size_t b64_cap = (pcm_len / 3 + 1) * 4 + 4;
    char *b64 = malloc(b64_cap);
    if (!b64) return -ENOMEM;
    size_t b64_len = 0;
    if (mbedtls_base64_encode((unsigned char *)b64, b64_cap, &b64_len,
                              pcm_data, pcm_len) != 0) {
        free(b64);
        return -ENOMEM;
    }

    /* 4. 拼 JSON 请求体（用 cJSON，别手拼字符串） */
    cJSON *root = cJSON_CreateObject();
    cJSON_AddStringToObject(root, "format", "pcm");   /* 裸 PCM，不要 wav */
    cJSON_AddNumberToObject(root, "rate",    16000);
    cJSON_AddNumberToObject(root, "channel", 1);
    cJSON_AddStringToObject(root, "cuid",    "openvela-superchild");
    cJSON_AddStringToObject(root, "token",   g_access_token);
    cJSON_AddNumberToObject(root, "len",     (double)pcm_len);  /* 原始字节数！ */
    cJSON_AddStringToObject(root, "speech",  b64);
    cJSON_AddNumberToObject(root, "dev_pid", 1537);
    char *body = cJSON_PrintUnformatted(root);
    cJSON_Delete(root);
    free(b64);
    if (!body) return -ENOMEM;

    /* 5. POST（复用 infra/http_proxy.h 或项目已有的 HTTPS 能力） */
    char *resp = NULL;
    size_t resp_len = 0;
    int rc = agent_https_post_json(BAIDU_ASR_URL, body, strlen(body),
                                   &resp, &resp_len);
    free(body);
    if (rc < 0) {
        AGENT_LOGE(TAG, "HTTPS 请求失败: %d", rc);
        return rc;
    }

    /* 6. 解析：先看 err_no，再看 result[0] */
    cJSON *json = cJSON_Parse(resp);
    free(resp);
    if (!json) {
        AGENT_LOGE(TAG, "返回不是合法 JSON");
        return -EIO;
    }

    cJSON *err_no = cJSON_GetObjectItem(json, "err_no");
    if (!cJSON_IsNumber(err_no) || (int)err_no->valuedouble != 0) {
        int code = err_no ? (int)err_no->valuedouble : -1;
        cJSON *msg = cJSON_GetObjectItem(json, "err_msg");
        AGENT_LOGE(TAG, "ASR 失败 err_no=%d msg=%s",
                   code, msg && msg->valuestring ? msg->valuestring : "?");
        cJSON_Delete(json);
        /* 3302 = 鉴权失败：清掉 token 让下次重换 */
        if (code == 3302) g_access_token[0] = '\0';
        return -EIO;
    }

    cJSON *result = cJSON_GetObjectItem(json, "result");
    cJSON *first  = cJSON_IsArray(result) ? cJSON_GetArrayItem(result, 0) : NULL;
    if (cJSON_IsString(first)) {
        /* 严格按 text_cap 截断，保证 UTF-8 不被切断 */
        strncpy(text_out, first->valuestring, text_cap - 1);
        text_out[text_cap - 1] = '\0';
    }
    cJSON_Delete(json);
    return 0;   /* 识别为空文本也返回 0，由上层决定怎么处理 */
}

static void baidu_asr_deinit(void) { /* 清敏感内存 */ }

static const voice_asr_ops_t g_baidu_asr_ops = {
    .name      = "baidu",
    .init      = baidu_asr_init,
    .recognize = baidu_asr_recognize_impl,
    .deinit    = baidu_asr_deinit,
};

int baidu_asr_register(void)
{
    return voice_asr_register(&g_baidu_asr_ops);
}
```

### 5.2 实现时容易踩的坑

| 坑 | 说明 |
|---|---|
| `len` 写成了 base64 长度 | 百度要的是**原始字节数**。写错会报 3300 或识别成乱码 |
| base64 缓冲没留余量 | 编码后长度是 `ceil(n/3)*4`，必须按这个开 buffer，否则越界 |
| 用 `format: "wav"` 但传的是裸 PCM | 百度会按 wav 解析，报 3308/3311 |
| token 只在 init 时换一次 | 百度 token 有效期 30 天，长期运行必须处理过期续期，并做**提前刷新**（例如剩余 <1 天就重换） |
| `text_out` 直接 `strcpy` | `text_cap` 是调用方给的，必须截断保护；中文还要防 UTF-8 截半 |
| token 明文长期驻留内存 | 尽量做敏感内存清理；至少不要打到日志里（框架有日志脱敏，但也别主动打） |

## 6. `baidu_tts.c` 实现要点

### 6.1 与 ASR 的主要差异

- 百度 TTS 是 **GET 形式**（参数走 query string），用 POST 也能带表单参数
- `tex` **必须 URL 编码**，中文尤其重要，否则报参数错误
- **出错时返回的是 JSON，不是音频** —— 所以要先看返回内容/`Content-Type` 再决定怎么解析。
  这是最容易踩的坑：把 JSON 当成 PCM 返回给播放器，会听到一段刺耳噪声
- 返回的音频要**先转成裸 PCM**（见 3.2 的 `aue` 选择与剥头逻辑）

### 6.2 骨架要点

```c
/* 参数（query string） */
tex=<urlencode(text)>   /* 必须 URL 编码 */
tok=<access_token>
cuid=openvela-superchild
ctp=1
lan=zh
spd=<语速 0-15>  pit=<音调>  vol=<音量>
per=<发音人>       /* 4 = 度丫丫（童声），需账号有授权；不可用则退回 0 */
aue=4              /* 4 = pcm；若拿不到就改 6(wav) 并剥掉头 */

/* 返回判定（关键） */
if (content_type 含 "json" 或 首字节是 '{') {
    /* 解析 err_no / err_msg，返回错误。绝不能当音频用 */
}
else {
    size_t skip = skip_wav_header(buf, len);   /* 见 3.2 */
    size_t pcm_len = len - skip;
    if (pcm_len > pcm_cap) return -ENOSPC;      /* 见 6.3 */
    memcpy(pcm_out, buf + skip, pcm_len);
    *pcm_len = pcm_len;
}
```

### 6.3 必须处理 `pcm_cap` 可能不够

`synthesize()` 的签名带 `pcm_cap`，说明**调用方给的缓冲是有限的**。
30 个汉字大约合成 5-8 秒音频，16kHz/16bit/单声道约 **160-256KB**。

**做法**：

1. 先量出 `voice_channel.c` 实际传入的 `pcm_cap` 是多大（`grep -n "voice_tts_speak" src/voice/voice_channel.c`）
2. 如果 cap 小于实际需要，**不要让接口失败**，而是改为：
   - 缩短文本（但回复本来就限 30 字，余地不大），或
   - 申请扩大该缓冲（改 `voice_channel.c`，属于必要改动），或
   - 在 TTS 里做「分句合成 + 多次回调」（仅流式路径可行）
3. **务必显式判断并返回 `-ENOSPC`，不要静默截断** —— 截断会产生半句话的爆音

## 9. 内存预算（128MB 是硬约束）

| 环节 | 估算 | 说明 |
|---|---|---|
| ASR 输入 PCM（3 秒） | ~96KB | 16k × 2B × 1ch × 3s |
| base64 后 | ~128KB | `ceil(96/3)*4` |
| JSON 请求体 | ~135KB | 加字段开销 |
| HTTP/TLS 缓冲 | ~64-128KB | 取决于 mbedtls 配置与分片 |
| **ASR 峰值** | **~400-500KB** | 加上 cJSON 解析树 |
| TTS 输出 PCM（6 秒） | ~192KB | 30 汉字大致 5-8 秒 |
| **TTS 峰值** | **~300KB** | 主要是输出缓冲 |

**结论**：单次请求峰值可控制在 1MB 量级，128MB 内存完全够用。但必须遵守三条：

1. **音频缓冲单次分配后复用**，不要每轮 `malloc`/`free`（碎片化在 RTOS 上很致命）
2. **HTTP 响应流式读写**，不要把整个响应再复制一份
3. **录音固定时长上限**（建议 3-5 秒），并给缓冲设硬上限，超了就拒绝新增而不是扩容

如果内存吃紧，按这个顺序砍：
关掉 AI Agent 的飞书通道（~108KB）→ 微信（~45KB）→ 先不开 `AI_AGENT_AUDIO_PREPROCESS`（~150KB）

## 10. 风险与预案

| 风险 | 可能性 | 预案 |
|---|---|---|
| `voice_start` 走流式，而百度后端只有非流式 | 中 | 用 3.3 节的「假流式」；成本很低 |
| `voice_channel.c` 传入的 `pcm_cap` 太小 | 中 | 显式返回 `-ENOSPC`；必要时把缓冲扩大（这是一处必要的上游改动） |
| 百度 TTS 的 `aue=4` 对当前账号不可用 | 中 | 改用 `aue=6` + 剥 WAV 头 |
| `per=4`（童声）无授权 | 中 | 退回 `per=0`（度小美）；童声只是音色偏好，不影响功能 |
| **HTTPS 证书验证失败** | **高**（2026-09-19 修正） | ⚠️ **原判「低」是错的。** 实测：板子**系统时间是 1970 年**（无 RTC，上电从 0 开始），而 TLS 证书校验必须判断"证书是否在有效期内"→ **必然失败**。另外 CA 也**不在 `/etc/ssl/certs`**（该目录不存在），实际在 `/resource/etc/ssl/curl/ca-certificates.crt`。修时间的三条路全被堵死（`date -s` 不支持、NTP 服务器写死为国外 `pool.ntp.org`、无任何 NTP 配置文件）→ **只能重编译换国内 NTP 服务器**。**详见 `R5操作卡.md` 第三节** |
| 实现卡住超过 3 天 | — | **果断停下**，用火山引擎基线继续推进主线，把百度后端降级为独立待办。不要让它阻塞整个项目 |
| 想改上游但又怕影响主线 | 低 | fork + 独立分支 + Kconfig 开关（默认关闭），主线不受影响 |

## 11. 常见错误速查

| 现象 | 最可能的原因 |
|---|---|
| ASR 报 3300 | 参数不对：`len` 写成了 base64 长度，或 `format` 与实际数据不符 |
| ASR 报 3302 | token 无效/过期，检查续期逻辑 |
| ASR 报 3308 / 3311 | `format: "wav"` 但传的是裸 PCM（应改 `format: "pcm"`） |
| ASR 返回空文本但 `err_no=0` | 音频太短或全是噪声——检查是不是没录到人声 |
| TTS 播放出来是刺耳噪声 | **把百度的错误 JSON 当成 PCM 返回了**，加内容类型判断 |
| TTS 声音是半句话/爆音 | `pcm_cap` 不够，你静默截断了。应返回 `-ENOSPC` |
| TTS 音调不对/语速飞快 | 把 WAV 头剥掉了但音频实际是 8kHz（用了 `aue=5`），或采样率不匹配 |
| 编译报 `cJSON.h` 找不到 | `packages/ai_agent` 的构建脚本没链 cJSON；照 `volc_asr.c` 的依赖声明抄 |
| 编译报 mbedtls 链接错误 | 同上，照 `volc_asr.c` 的 include 与依赖抄 |
| 运行中随机死机/重启 | 内存不足或缓冲越界。查 `free`、开 `CONFIG_DEBUG_*`，重点看 base64 与 JSON 的 buffer 大小 |
| token 换不来但 Key 是对的 | 检查是否用 `client_credentials`，以及 API Key/Secret Key 有没有贴反 |

## 12. 与 PC 试验台的对应关系

| 环节 | PC 试验台（`prototype/`） | 板端百度后端 |
|---|---|---|
| ASR 输入 | wav 文件，读文件 + 校验规格 | 裸 PCM，由 `audio_capture` 提供 |
| ASR 请求体 | `format: "wav"` | `format: "pcm"` |
| TTS 输出 | `aue=6`（wav），落盘试听 | `aue=4`（PCM），直接交给播放 |
| 错误码处理 | `asr.py` 的 `ERROR_HINTS` / `tts.py` 的 `TTS_ERROR_HINTS` | 建议把同一套错误码语义搬过去，日志更好读 |
| token 缓存 | 落盘到 `.baidu_token_cache.json` | 内存缓存 + config store |

**注意**：PC 与板端在 `format` / `aue` 上**故意不一致**，因为两端拿到的数据形态不同。
这不是实现不一致，改动时别"顺手对齐"。
